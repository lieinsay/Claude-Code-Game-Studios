## Overview

飞艇家园 Hub 是《云海织航》中玩家每天醒来、整备、回来、整理和居住的地方。它不是一个菜单或载具属性面板，而是一个横版剖面可步行飞艇内部——2-4 个小舱室或区域、可交互的工作台与货架、伙伴驻点、模块接口和储物空间——玩家在其中行走、靠近、确认、使用，感受"这是我的船，这是我的家"。作为核心循环的起点和终点，Hub 承载着每次出航前的整备（查看情报、调整货物、检查模块），也承载着返航后的归位（拆包战利品、存入仓库、修复船体、看见世界变化在船上留下痕迹）。没有这个系统，飞艇就只是一个会移动的图标，玩家不会感觉自己住在空海里——他们会感觉自己在菜单之间跳转。

## Player Fantasy

飞艇家园 Hub 服务的幻想是三层交织的：**归港之锚、亲手准备的意志、船是你的航志**。

**归港之锚**：在空海世界里，飞艇是唯一绝对安全的地方。关舱门不是退回菜单，而是回到自己的地方。高风险撤离后推开舱门的瞬间——暖光仍在、引擎低鸣、架子上的东西没变——船用沉默说：你回来了。玩家不是把战利品"点击存入仓库"，而是走到货架前一件件归位。手指搭上熟悉的舱壁时，紧张才真正褪去。船是空海中唯一不会背叛你的坐标。

**亲手准备的意志**：出发前，玩家亲身走过每一站——在情报台前读一遍航线风险，经过伙伴驻点时听一句侦察简报，在模块接口前确认状态灯全绿，扫一眼货舱确保空间够带新东西回来。这不是填表格、点菜单，而是一套身体感的整备仪式。推开舱门面对航线图的那一刻，玩家心里清楚：这不是碰运气——我已经准备好了。

**船是你的航志**：船不只是家和整备站，它是活着的航行日志。修好灯塔后回到船上，墙上旧航线图多了一条手绘白线；船体旧伤旁出现新的修补痕迹；带回的异岛矿物在架子上有自己的一格位置。船用沉默的方式记录你为世界做了什么，也让每次归来不是循环重置，而是叙事推进。你修好世界——船负责记住。

参考游戏的情感基准：《方舟：生存进化》第一次拥有自己基地的归属感和身份认同，但不是通过宏大规模实现——而是通过细节痕迹、熟悉动线和每次归来的安心感。与《方舟》不同的是，这里的"家"会移动、会记录世界变化、会把"你修好了什么"写在船体上。

## Detailed Design

### Core Rules

**R1 — Hub 是场景根，不是 UI 容器。** Hub 拥有飞艇内部的空间布局、碰撞体、可行走区域和所有 Interactable 实例的注册。移动系统向 Hub 查询 walkable areas 和 interaction anchors。Hub 内部的所有步行和交互是身体化的——不能退化为"菜单之间走路"。

**R2 — 交互锚点注册契约。** Hub 中每个可交互对象必须在 InteractionRegistry 中注册为 Interactable，提供：
- 稳定 ID（由内容注册表分配，格式 `hub.interactable.[name]`）
- `anchor_radius`、`priority`、`interaction_type`
- `is_enabled()` — 反映站点当前可用性
- `get_display_hint()` — 返回站点名称 + 状态摘要（如 `"仓库 · 920/1000"`）

`use_requested` 信号到达后，Hub 将交互委派给对应领域系统。Hub 本身不拥有拆包、购买、情报查询、修复或模块管理的逻辑。

**R3 — MVP 站点清单。** Hub 必须包含以下可交互站点：

| # | 站点 | 交互类型 | 领域系统 | 位置 |
|---|------|---------|---------|------|
| 1 | 情报台 | `read` | 玩家知识与情报 | 驾驶舱 |
| 2 | 伙伴驻点 | `talk` | 伙伴功能与关系 | 生活舱 |
| 3 | 模块接口 A（侦察模块） | `use` | 飞艇模块与船体状态 | 工程舱 |
| 4 | 模块接口 B（货仓/维修模块） | `use` | 飞艇模块与船体状态 | 工程舱 |
| 5 | 飞艇仓库/货架 | `open` | 资源、货物与容量 | 工程舱 |
| 6 | 货舱堆货区 | `open` | 资源、货物与容量 | 货舱 |
| 7 | 舱门 | `use` | 航图与航线规划 | 驾驶舱 |
| 8 | 舵轮 | `use` | Hub 自身（触发自主飞行） | 驾驶舱 |
| 9 | 休息点（床铺/吊床） | `rest` | —（MVP 无机械功能） | 生活舱 |
| 10 | 船体维修点 | `repair` | 世界修复与解锁 / 飞艇模块与船体状态 | 工程舱 |

**R4 — 飞船移动分两种模式。** Hub 支持两种离开着陆点的方式：

**Mode A — 固定航线移动（舱门）：** 玩家走到舱门 → 交互触发"准备出航"确认 → 确认后进入 `departure_locked`（移动冻结、简短动画 ~2s）→ Hub 将当前状态包传递给航图系统 → 场景切换到航线图 → 玩家选择已有航线出发。这是安全、可预测的移动方式。

**Mode B — 自主飞行（舵轮）：** 玩家走到舵轮 → 交互触发"自主操控"确认 → 确认后进入 `departure_locked` → 场景切换到俯视/地图式自由移动界面 → 玩家自主选择移动方向，进入未探明区域。没有航线时仍可使用——这是"向未知出发"的入口。

自主飞行永远可用（不依赖航线或模块），但有明确代价以保护 Pillar 1（规划先于冒险）：(a) **遭遇风险显著高于固定航线**——未经测绘的路径更容易触发危险事件（具体倍率由 `航行与路线风险` #10 定义）；(b) **不产生航线知识**——自主飞行经过的区域不会自动转化为已知航线信息。固定航线移动在有已知航线时更安全、更高效（有风险标注和预期结果）；自主飞行适合开拓新区域，但每次都是冒险而非规划。两种模式的选择本身就是玩家的策略决策。

**R5 — 返航不是重置。** 返航后 Hub 恢复到 `landed` 状态，但保留：（a）货舱内容变化（或战后损失结果），（b）模块安装状态（含可能的航行损伤），（c）仓库内容变化，（d）世界修复痕迹更新。玩家每次回来都感觉是"续上生活"，不是"重新开始"。

**R6 — 舱室存在性门控。** 货舱在货物/维修模块未安装时，该区域在视觉上不存在——飞艇对应位置是外部缺口或空白，强化"飞艇是可拼装成长的家"。安装模块后，新舱室"拼装"到船体上，`room_exists(cargo_hold) = true`，玩家可步行进入。模块接口显示安装状态（空槽 / 已安装 / 已损伤）。门控不是隐藏 UI——是物理存在性的变化，让玩家"看到"飞艇在成长。

**R7 — 最低生活痕迹。** Hub 暴露一组可持久化的"痕迹锚点"——少量二进制/枚举状态标记，由存档系统在 `progress.airship` 快照包中保存和恢复。至少包括：
- 情报台海图状态（干净 → 有笔记 → 写满了）
- 货架占用状态（空 → 部分满 → 满）
- 生活舱个人物品存在（无 → 有）
- 船体修补痕迹（无 → 有旧伤 → 有新伤+旧伤补丁）

这些标记不产生机械效果，只为满足存档 GDD 的"这仍是我的家"最低生活痕迹要求。MVP 中痕迹锚点为泛化密度/状态计数器（如货架从空到满、船体从无伤到有修补）——传达"这里发生过什么"而非具名记录"哪次修复产生了这条痕迹"。具名叙事痕迹（如"星芒港灯塔航线"海图标记）属于 Post-MVP 扩展。

**R8 — 玩家生成点。** 首次加载（新游戏/读档）：玩家生成在舵轮附近的甲板中心——第一眼看到舵轮和窗外云海，暗示"前方是航程"。返航后：玩家生成在舱门——推门进舱的瞬间是"归港之锚"的核心情感节拍（"推门进舱门的瞬间——暖光仍在、引擎低鸣"）。生成后玩家自然走向舵轮完成停靠，然后进入返航流。

**R9 — 出航确认信息契约。** 玩家在舱门（Mode A）或舵轮（Mode B）确认出航时，确认对话框必须展示出航摘要。确认对话框仅为信息展示——不强制要求访问任何站点，不阻断出航。未访问站点以警告形式列出并附带可感知的轻量机械后果（非惩罚，而是信息不对称的自然代价），玩家自主判断准备是否充分：

- **整备站点检查清单**：列出关键站点的访问状态——情报台（已读/未读）、伙伴驻点（已交互/未交互）、货舱（已检查/未检查）。未访问项显示提醒文本及具体后果，如：
  - 情报台未读：航线风险评级标注"未知" + 本次出航遭遇率 +10%（来源：`航行与路线风险` #10 定义的 `uninformed_departure_penalty`）
  - 伙伴驻点未交互：不提供本次出航的侦察简报（无额外情报提示）
  - 货舱未检查：出航确认中货舱容量显示"未确认"而非精确数值——可能在探索中意外满仓
  - 模块未检查（任一槽位）：该模块本次运行效率降至 95%（来源：`飞艇模块与船体状态` #8 定义的 `unchecked_module_efficiency`）
- **航线风险评级**：若情报台已交互，显示从玩家知识与情报系统获取的当前风险摘要；否则标注"未知"。
- **仓库剩余容量**：从资源系统查询当前仓库余量（如 `920/1000`），让玩家在出航前判断是否有足够空间接收返航战利品。
- **货舱剩余容量**：从资源系统查询；若货舱模块未安装，标注"无货舱"。
- **模块完好度摘要**：正常 / 有损伤 / 未安装（按模块槽位逐项列出）。

软机械后果的设计原则：(a) 每一项都是信息透明且提前告知的——对话框中标注后果而非事后追溯；(b) 每一项都是轻量的（5-10% 范围）——不会让跳过整备变得惩罚性；(c) 玩家始终可以自主选择是否接受这些代价。确认按钮始终可点击。

"仅警告不阻断"保护 Pillar 1（规划先于冒险）——让玩家在知情的前提下自主判断是否准备充分，而非强制执行固定仪式流程。软机械后果让"知情"具有决策意义：警告不只是提醒文本，而是有可感知差异的选择。此机制需要玩测验证长期仪式可持续性——若玩家反馈整备流在重复循环后仍空洞，将数值从 5-10% 升至 10-15%。

### States and Transitions

**停靠状态（Hub Docking State）：**

| State | Meaning | Allowed Actions |
|-------|---------|-----------------|
| `landed` | 着陆中（空港/野外/未知岛屿），默认状态 | 自由行走、所有站点交互、整备 |
| `departure_locked` | 出航确认后，动画播放中 | 移动冻结，~2s |
| `in_transit` | 航行中（固定航线或自主飞行） | Hub 内部不可进入（玩家在航图/自由飞行或探索场景） |
| `arrival` | 抵达动画播放中 | 移动冻结，然后自动转入 `landed` |

Transitions:
- `landed → departure_locked`：玩家在舱门确认出航（Mode A）或舵轮确认自主飞行（Mode B）
- `departure_locked → in_transit`：动画完成，交接给航图系统（Mode A）或自由飞行界面（Mode B）
- `departure_locked → landed`：航图系统拒绝出航（Mode A — 无有效航线）或自由飞行界面加载超时（Mode B），恢复移动控制
- `in_transit → arrival`：航行/探索结束，返航触发
- `arrival → landed`：抵达动画完成，玩家恢复控制

**舱室状态（Room State，每个舱室独立）：**

| State | Meaning |
|-------|---------|
| `exists` | 舱室存在且可步行进入、站点可交互 |
| `not_exists` | 舱室不存在——该区域在视觉上是飞艇外部缺口/空白 |

- 货舱在货仓/维修模块未安装时为 `not_exists`——视觉上缺失，安装模块后拼装到船体，变为 `exists`
- 工程舱始终 `exists`（模块接口即使空槽也可查看）
- 驾驶舱、生活舱始终 `exists`

**模块槽状态（Module Slot State，每个槽位独立）：**

Hub 显示模块的 `visible_state`（由模块系统 #8 拥有和维护）。Hub 不拥有状态机逻辑——仅负责根据模块系统的状态值驱动视觉表现和交互可用性。

| State | Meaning | Hub 视觉表现 |
|-------|---------|-------------|
| `empty` | 未安装模块 | 空安装位支架+轮廓线，状态灯灭 |
| `installed` | 模块已安装，正常工作 | 状态灯绿，模块完整外观 |
| `damaged` | 模块已安装但有损伤（已检查确认） | 状态灯黄，模块外观有损伤痕迹 |
| `unchecked` | 模块返航后尚未检查（效率 0.95） | 状态灯黄闪（缓慢），模块外观正常但叠加"?"标记——提示玩家需检查 |

> **Hub 与模块系统的边界**：`unchecked` 状态由模块系统 #8 定义和管理。Hub 仅显示该状态并触发检查/维修交互。对于 `room_exists()` 门控判定：`unchecked` 被视为已安装（同 `installed` 和 `damaged`），因为模块物理上存在于槽位中。模块槽位的交互行为（检查 vs 维修 vs 卸下）根据 `visible_state` 不同而变化——具体交互逻辑由模块系统 #8 拥有。

**站点状态（Station State，每个交互站点独立）：**

| State | Meaning |
|-------|---------|
| `ready` | 可交互 |
| `busy` | 正在被交互（UseLocked） |
| `disabled` | 暂时不可用（如伙伴未招募时驻点闲置、模块未安装时货舱不可进入） |

Transitions:
- `ready → busy`：玩家执行 Use 且领域系统返回 `UseLocked`
- `busy → ready`：领域系统完成交互并释放锁
- `ready → disabled`：站点条件失效（如模块被摧毁、伙伴离船、货舱变为 `not_exists`）
- `disabled → ready`：站点条件恢复（如模块重新安装、伙伴归船）
- `busy → disabled`：交互进行中站点条件失效——当前交互完成（领域系统正常返回结果），释放锁后站点降为 `disabled`。下次交互请求时判定为 `disabled`。条件仅在交互开始前重新评估——Godot 单线程游戏循环保证交互回调期间条件不会改变，因此"交互进行中条件突变"为不可能竞态。

### Interactions with Other Systems

| System | Hub 提供 | Hub 接收 | 边界 |
|--------|---------|---------|------|
| `玩家移动与交互` | walkable areas、room bounds、所有 Interactable 注册 | `use_requested` 信号、focus 事件、movement state | Hub 拥有空间和锚点；移动系统拥有输入解释和焦点判定 |
| `资源、货物与容量` | 仓库和货舱的物理访问点、当前容量值（供 UI 展示） | 容量状态查询、拆包结果 | 资源系统拥有容量规则和物流操作；Hub 拥有空间位置 |
| `本地存档与世界状态持久化` | `progress.airship` 快照包：停靠状态、舱室状态、模块槽状态、站点状态、痕迹锚点标记 | 保存/加载触发 | Hub 拥有状态；存档系统拥有序列化和恢复。快照仅存储独立变量（`module_slot_state`、`trace_anchors`），`room_state` 和 `station_state` 在加载时通过 `room_exists()` 和跨状态机耦合规则重新派生——不双重存储。派生规则：`station_state` 根据站点条件派生为 `ready` 或 `disabled`；`busy` 是瞬态交互状态，不持久化——加载时统一派生为 `ready`（交互已中断，释放锁）。 |
| `内容数据与状态注册表` | — | 舱室/站点/模块槽的稳定 ID 定义 | 注册表拥有静态定义、Schema 和查询契约 |
| `飞艇模块与船体状态`（#8） | 模块槽物理位置、完整槽位状态（`empty` / `installed` / `damaged`）、当前货舱容积值 | 模块效果（容积加成、damaged 时效果打折）、安装/卸下操作 | 模块系统拥有模块定义和效果逻辑；Hub 拥有物理槽位状态（3 态枚举，非布尔值——`damaged` 已安装的模块仍计为 `installed` 用于 room_exists 判定，但模块系统自行计算效果打折） |
| `航图与航线规划`（#9） | "舱门激活"事件 + 当前 Hub 状态包（着陆位置、模块安装、货舱装载）→ Mode A | 目的地选择 → Hub 转入 `in_transit`；或拒绝出航 → `landed` | Hub 拥有过渡触发和状态传递；航图系统拥有地图和路线选择 |
| `航行与路线风险`（#10） | "舵轮激活"事件 + 当前 Hub 状态包 → Mode B（自主飞行）。Hub 声明 Mode B 遭遇风险显著高于固定航线且不产生航线知识；航行系统定义具体倍率 | 自主飞行结果 → Hub 转入 `in_transit` | Hub 拥有过渡触发和代价契约方向；航行系统拥有自由飞行规则、风险倍率和 EncounterContext 生成 |
| `伙伴功能与关系`（#15） | 伙伴驻点的物理位置和伙伴在场状态 | 伙伴可用性、侦察返回简报 | Hub 拥有物理站点；伙伴系统拥有关系和能力逻辑 |
| `世界修复与解锁`（#13） | 船体维修点的物理位置 | 维修操作、船体外观更新 | Hub 拥有维修点访问；修复系统拥有消耗和结果 |
| `UI / HUD / 航图界面`（#16） | 站点交互触发 UI 打开请求、HUD 关键指标数据（船体完整性、仓库余量、货舱装载） | 模态/overlay 状态（阻断世界交互） | Hub 提供数据；UI 负责呈现和模态管理 |

### Spatial Layout (MVP)

双层四舱布局——上层驾驶舱 + 生活舱，下层工程舱 + 货舱，中部楼梯/梯子连通：

- **驾驶舱**（上层左）：舵轮（视觉锚点）+ 情报台 + 舱门。决策与出航的核心——情报读完转身即舱门。
- **生活舱**（上层右）：伙伴驻点 + 休息点（床铺/吊床）。视觉温度偏暖，与驾驶舱形成"工作/私密"分区。
- **工程舱**（下层左）：模块接口 A + B + 船体维修点 + 仓库货架。技术站点集中（管线和仪表板统一视觉）与长期存储（整齐货架靠左墙）。仓库在此舱室保证始终可访问——不依赖货舱模块门控。
- **货舱**（下层右）：货舱堆货区。板条箱和货物堆叠，整齐码放，与工程舱的仓库货架形成视觉区分（临时运输货物 vs 长期存储材料）。货舱存在性由货舱模块门控（R6）。

出航整备流（收紧节奏）：生活舱 → 驾驶舱 → 下楼 → 工程舱（模块检查+仓库查看）→ 货舱（堆货区检查）→ 上楼 → 驾驶舱出航
返航归位流（释放节奏）：舱门进入 → 舵轮停靠 → 下楼 → 货舱拆包（堆货区）→ 工程舱查看+仓库归位 → 上楼 → 生活舱休息

## Formulas

### Hub-Owned Formulas

The `room_existence` formula is defined as:

`room_exists(room_id) = room_base_exists(room_id) OR (room_required_module(room_id) ≠ null AND module_installed(room_required_module(room_id)))`

Where `room_required_module(room_id) → module_id | null` is the room-to-module mapping function.

**MVP Room-to-Module Mapping:**

| room_id | room_base_exists | room_required_module |
|---------|-----------------|---------------------|
| `cockpit` | true | null |
| `living_quarters` | true | null |
| `engineering_bay` | true | null |
| `cargo_hold` | false | `cargo_module` |

**Variables:**

| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| room_base_exists | — | bool | true/false | 舱室默认是否存在（驾驶舱/生活舱/工程舱 = true；货舱 = false） |
| room_required_module | — | function | module_id \| null | 该舱室依赖的模块 ID（null = 无条件存在）。MVP 中仅 `cargo_hold → cargo_module` |
| module_installed | — | bool | true/false | 所依赖的模块当前是否已安装。`module_installed(module_id) = (slot_state[module_id] == installed) OR (slot_state[module_id] == damaged) OR (slot_state[module_id] == unchecked)` |

**Output Range:** true/false。当前 MVP 仅货舱受模块门控：`room_exists(cargo_hold) = false OR (cargo_module ≠ null AND module_installed(cargo_module))`。其余舱室 `room_required_module` 为 null，`room_base_exists` 为 true，始终返回 true。
**Example:** 货仓/维修模块安装在模块接口 B 时，`module_installed(cargo_module) = true`，货舱从视觉缺失变为 `exists`——新舱室拼装到船体上。

---

The `departure_lock_timer` formula is defined as:

`departure_lock_duration = clamp(base_lock_duration, 1.5, 3.0)`

**Variables:**

| Variable | Symbol | Type | Range | Description |
|----------|--------|------|-------|-------------|
| base_lock_duration | — | float | 1.5–3.0s（安全范围） | 出航锁定动画时长，默认 2.0s。启动时 validation 检测：`is_nan(value)` 或 `value < 1.0` 或 `value > 5.0` → 拒绝并使用默认值 2.0s。NaN 不与任何比较相等，必须显式检查。公式体内 `clamp(value, 1.5, 3.0)` 提供运行时最后防线。 |

**Output Range:** 1.5s 到 3.0s。Tuning Knob 可在此范围内调整，但不建议低于 1.0s——太短会削弱"有意操作"感。若配置值在 1.0–1.5 或 3.0–5.0 范围，启动验证通过但运行时 clamp 进一步约束——设计者应收到警告。
**Example:** `departure_lock_duration = clamp(2.0, 1.5, 3.0) = 2.0s` → 玩家确认出航后，移动冻结 2 秒，动画播放舱门开启/引擎点火，然后场景切换到航图。

### Sections That Need No Formula

以下设计元素已在 Detailed Design 中以状态表和规则形式完整定义，不需要额外公式：
- 停靠状态机（`landed → departure_locked → in_transit → arrival → landed`）
- 站点状态机（`ready / busy / disabled`）
- 模块槽状态机（`empty / installed / damaged`）
- 最低生活痕迹标记（二进制/枚举，无计算）
- 出航状态包（数据组装契约，非计算）

## Edge Cases

**状态转换中断：**

- **If 存档在 `departure_locked` 期间触发**: 捕获状态为 `departure_locked`，但 `departure_locked` 不是稳定边界。重载时回到 `landed`，出航确认丢失（安全降级）。
- **If 浏览器 `pagehide` 在 `arrival` 动画中触发**: best-effort 存档捕获 `in_transit`。重载时重新触发 arrival 动画，然后转入 `landed`。
- **If `departure_locked` 动画期间游戏崩溃且无存档**: 重启后 Hub 回到最近稳定存档（通常 `landed`）。出航确认丢失——可接受。
- **If `departure_locked` 持续超过 `departure_lock_duration * 3`（看门狗超时）**: 动画系统未发射完成信号（着色器挂起、资源加载失败等）。看门狗强制恢复 Hub 为 `landed`、解除移动冻结、写入错误日志并显示"出航中断"提示。这是单线程 Web 环境的必要最后防线——不依赖外部信号完成。

**零值/空值/极限值：**

- **If 所有站点均为 `disabled`（无模块、无伙伴、无 intel）**: Hub 仍可操作——玩家可自由行走、使用休息点、从舱门出航。出航不依赖任何站点启用。
- **If 所有模块槽均为 `empty`**: 货舱 `not_exists`（视觉上缺失）。工程舱仍可进入，模块接口显示空槽。舱门和舵轮功能不受影响。
- **If `departure_lock_duration` 被错误配置为 0 或非数值**: 启动时 validation 检测：`is_nan(value)` 或 `value < 1.0` 或 `value > 5.0` → 拒绝并使用默认值 2.0s。NaN 不与任何数值比较相等（`NaN < 1.0` 为 false），必须显式检查。运行时 `clamp(base_lock_duration, 1.5, 3.0)` 提供最后防线——若值在 1.0–1.5 或 3.0–5.0 范围内，启动验证通过但运行时 clamp 会进一步约束。设计者调至此范围时应收到警告，但不视为错误。

**输入竞态：**

- **If 玩家在 `departure_locked` 期间连按 Use**: Hub 请求移动系统进入 `Rooted`，所有站点报告 `disabled`。Use 被阻断为 `target_disabled`。
- **If 玩家在确认出航后立即按移动键**: `departure_locked` 触发 `Rooted`，移动系统忽略所有移动输入。
- **If 玩家在 `departure_locked` 的 2s 内再次对舱门按 Use**: 舱门 `is_enabled()` 返回 false，Use 被阻断为 `target_disabled`。不会重复触发出航。

**模块相关边界：**

- **If 航行中货舱模块被摧毁**: 返航 `arrival` 时 Hub 检测到 `cargo_module` 从 `installed` 变为 `empty` 或 `damaged`。货舱内容按资源系统规则处理（部分损失 + 可回收货箱）。货舱变为 `not_exists`（视觉上该区域消失，船体对应位置出现缺口/破损）。维修点标出需修复槽位。
- **If 玩家在货舱有货物时试图卸下货舱模块**: 模块接口查询 `get_cargo_bay_usage()` → `used_volume > 0` → 卸下被拒。UI 显示"请先清空货舱"并置灰卸下按钮。卸下货舱模块意味着该区域从船体移除，不能在有内容物时执行。
- **If 模块槽状态为 `damaged` 但模块仍 `installed`**: `room_exists()` 检查的是 `module_installed`，不是完好度。damaged 但已安装的模块——货舱仍存在且可进入。模块效果打折由模块系统自行决定——Hub 不拥有此判定。

**自主飞行相关：**

- **If 玩家在舵轮确认自主飞行但地图/自由飞行场景加载失败**: 场景过渡系统需保证原子性。若超时：保留在 `departure_locked`，显示错误提示，恢复到 `landed`。
- **If 玩家无任何已知航线，使用舵轮自主飞行进入未知区域**: 这是正常流程——自主飞行不依赖航线。但自主飞行不产生航线知识（经过的区域不会自动转化为已知航线），且遭遇风险显著高于固定航线（具体倍率由 `航行与路线风险` #10 定义）。重复自主飞行至同一区域不会使其变得更安全——每次都是新的冒险。
- **If 固定航线和自主飞行同时可用**: 玩家在 Hub 中自由选择——走到舱门（Mode A：安全高效 + 积累航线知识）或走到舵轮（Mode B：可进入未知但遭遇风险更高 + 不积累航线知识）。两个站点同处驾驶舱，选择本身就是策略决策——权衡安全与开拓。

**场景切换失败：**

- **If 航图系统拒绝出航**（无有效航线、超重等）: `departure_locked → landed` 转换。Hub 从航图系统收到拒绝原因码，显示提示，恢复移动控制。
- **If 航图场景加载失败**: 场景过渡系统需保证原子性——新场景未就绪前 Hub 不离开 `departure_locked`。若超时：保留在 `departure_locked`，显示错误提示，恢复到 `landed`。
- **If 返航后 Hub 场景加载失败**: 场景过渡系统责任。若 `progress.airship` 快照损坏：Hub 使用安全默认状态（全部站点 `ready`、生成点甲板中心、痕迹锚点初始值）并显示警告。

**与移动系统的边界：**

- **If `departure_locked` 开始前玩家已被 Rooted**（如正在与情报台交互）: 舱门交互前检查是否有活跃 `UseLocked`——若有，拒绝出航（`target_busy`）。不允许嵌套锁定。
- **If `arrival` 动画播放时 InputClosed**（overlay 可见）: `arrival → landed` 转换仍完成，但玩家因 InputClosed 无法移动。InputOpen 时自然恢复。状态机不依赖输入门。
- **If 玩家在 `departure_locked` 中恰好站在 reach_limit 边缘**: 一旦进入 `departure_locked`，不再重新评估可达性。Rooted 冻结优先级高于距离检查。

## Tuning Knobs

| Knob | Type | Default | Safe Range | What It Affects | Too Low | Too High |
|------|------|---------|------------|-----------------|---------|----------|

## Visual/Audio Requirements

### 视觉需求

- **横版剖面飞艇内部**：2D side-view，前景（栏杆、管线）、中景（玩家行走层）、后景（舱壁、窗户、窗外云海流动）三层纵深。每个舱室有独立的材质温度和色调——驾驶舱冷色金属+海图+仪表，生活舱暖光+布质+私人物品，工程舱管线+金属+状态指示灯，货舱木箱+货架+堆叠感。
- **舱室拼装动画**：货舱模块安装后，飞艇对应位置从缺口/空白状态过渡到完整舱室——简短视频序列或程序化过渡（~1-2s），让玩家"看到"家在成长。
- **舱室缺失状态**：货舱模块未安装时，对应位置显示飞艇外部缺口——可见云海天际线、结构框架裸露——清楚传达"这里还能扩建"。
- **痕迹锚点视觉**：4 个可持久化标记的视觉变化——海图从干净到写满笔记（3 档）、货架从空到满（3 档）、生活舱个人物品从无到有（2 档）、船体修补痕迹积累。变化应是渐进、累积的，不是一次性替换。
- **出航锁定动画**：确认出航后 ~2s 的过渡动画——舱门模式：舱门开启+引擎点火；舵轮模式：舵轮特写+船体转向。动画播放期间移动冻结。
- **返航抵达动画**：到达目的地后 ~1-2s 的着陆/停靠动画，然后 Hub 恢复控制。视觉上传达"到家了"的安稳感。
- **状态指示灯**：模块接口用颜色编码显示安装状态（绿=正常、黄=损伤、灭=空槽）。站点可用/不可用通过视觉高亮/灰化区分。
- **风格约束**：服从"航路修复主义"锚点——修补痕迹可见、拼接感、旧物改造感。不追求崭新或完美。服从 WebGL 2 / Compatibility renderer 性能预算——2D sprite + 少量 shader，不做大量粒子或后处理。

### 音频需求

- **飞艇环境声**：低音量持续引擎低鸣（停靠时较轻、航行中加重），作为 Hub 的听觉基底。
- **舱门开/关**：金属铰链声 + 气压变化声——区分出航和返航的听觉仪式感。
- **舵轮交互**：木质/金属转动声，确认自主飞行时音调升高——传达"掌控方向"的感觉。
- **模块拼装**：舱室拼装到船体时的机械锁定/铆接声——短促、有力、一次性的确认音。
- **站点交互**：每个站点 Use 时轻量反馈音（点击/确认音），不抢注意力。
- **返航抵达**：引擎减速 + 着陆缓冲声——与 departure_lock 的开场音形成闭环。
- **音量约束**：所有 Hub 音频不盖过背景音乐，MVP 不做空间音频（Web 约束）。

### 性能策略

- **纹理图集打包**：Hub 场景所有 sprite 纹理必须合并为图集，目标 draw call ≤ 10。未合图状态下每个 sprite 为独立 canvas item，draw call 可达 20-30，WebGL 2 渲染管线压力线性增长。
- **场景资源驻留**：Hub 场景在前往航图/探索期间保持内存驻留（`ResourceLoader` 不卸载），仅切换活动场景。避免返航时完整重载造成的 2-5s 等待。代价为 Hub 资产（~50-65MB）与航图/探索场景资产共享内存预算。
- **首屏加载**：Hub 为首个玩家可见场景，所有 Hub 资产 + Godot Web 引擎（~15-20MB 压缩）需在首屏可见前下载。需提供加载进度指示。

## UI Requirements

### HUD 常驻指标

在 Hub 场景中，HUD 必须持续展示以下关键指标（数据由 Hub 提供，UI 系统负责呈现）：

| 指标 | 数据来源 | 显示方式 |
|------|---------|---------|
| 船体完整性 | 飞艇模块与船体状态（#8） | 分段条形（3-5 段），颜色编码（绿/黄/红） |
| 仓库余量 | 资源、货物与容量（#5） | 数值 + 小条形（如 `920/1000`） |
| 货舱装载 | 资源、货物与容量（#5） | 数值 + 小条形（如 `320/500`）；货舱模块未安装时显示"无货舱" |

### 站点交互面板契约

站点交互面板由 UI 系统（#16）拥有，Hub 提供以下契约约束：

- **模态级别**：情报台（read）和仓库（open）为非模态面板——玩家可在阅读/整理时保持移动感知；模块接口（use）和舱门/舵轮（use）为模态面板——确认操作前阻断移动。
- **面板内容**：每个站点面板从 `get_display_hint()` 获取标题和状态摘要；具体内容由对应领域系统填充。
- **打开/关闭**：`use_requested` 信号触发面板打开；领域系统返回结果或玩家手动关闭后面板消失。`departure_locked` 期间所有面板强制关闭。

### 出航确认对话框

（见 R9 — 出航确认信息契约）

确认对话框必须包含：整备站点检查清单、航线风险评级、货舱剩余容量、模块完好度摘要。Mode A（舱门→固定航线）和 Mode B（舵轮→自主飞行）使用不同的视觉呈现：

- **Mode A**：显示航线名称 + 风险标注 + 预计到达信息（来自航图系统）
- **Mode B**：显示"自主飞行 — 进入未知区域"警告 + 当前朝向提示

### 无障碍最低要求

- 模块槽状态指示灯（绿=正常、黄=损伤、灭=空槽）必须同时使用形状区分（如 ✓ / ⚡ / ○），不可仅依赖颜色
- 站点 `disabled` 状态必须同时以灰化 + 文本标签呈现，不可仅依赖颜色
- 确认对话框中的所有警告文本必须可被屏幕阅读器访问
- HUD 数值变更必须有非颜色反馈（如容量条变化时轻微闪烁或数值跳动）

### 性能约束

- HUD 刷新频率不超过交互状态变化频率（按需更新，非每帧轮询）
- 站点面板内容按需加载（懒加载领域数据），不预加载所有站点数据

## Acceptance Criteria

**核心规则覆盖（R1-R9）：**

- **GIVEN** Hub 场景已加载，**WHEN** 玩家在飞艇内移动，**THEN** 碰撞体约束玩家行走范围，且每个交互步骤发生在场景中而非 UI 面板跳转。（R1）
- **GIVEN** Hub 已初始化，**WHEN** 查询 InteractionRegistry，**THEN** 返回恰好 10 个注册项，每项含 stable_id、anchor_radius、priority、interaction_type、is_enabled()、get_display_hint()。（R2）
- **GIVEN** Hub 场景就绪，**WHEN** QA 逐站检查，**THEN** 情报台/伙伴驻点/模块接口A/模块接口B/仓库货架/货舱堆货区/舱门/舵轮/休息点/船体维修点全部存在且 interaction_type 匹配设计表。（R3）
- **GIVEN** landed 状态且玩家在舱门 anchor_radius 内，**WHEN** 按 Use，**THEN** 弹出确认提示；确认后进入 departure_locked（移动冻结），2.0s 后场景切换至航图（Mode A — 固定航线）。（R4）
- **GIVEN** landed 状态且玩家在舵轮 anchor_radius 内，**WHEN** 按 Use，**THEN** 弹出"自主操控"确认提示；确认后进入 departure_locked，2.0s 后场景切换至俯视/地图自由移动界面（Mode B — 自主飞行）。（R4）
- **GIVEN** 出航前向仓库存入 50 铁矿石，**WHEN** 返航后检查仓库，**THEN** 铁矿石仍为 50（未被重置）。（R5）
- **GIVEN** cargo_module 未安装，**WHEN** 玩家查看飞艇对应位置，**THEN** 货舱区域在视觉上不存在（船体外部的缺口/空白）；安装模块后该区域拼装到船体上且可步行进入。（R6）
- **GIVEN** 完成一次世界修复（修灯塔），**WHEN** 返航后检查船体维修点，**THEN** 船体出现新的修补痕迹标记。（R7）
- **GIVEN** Hub 场景加载完成，**WHEN** 玩家首次生成，**THEN** 位置在舵轮附近甲板中心，第一视角可见舵轮和窗外云海。（R8）
- **GIVEN** 玩家完成航行/探索后返航，**WHEN** arrival → landed 转换完成，**THEN** 玩家生成在舱门位置，第一视角面对舱门——随后可走向舵轮完成停靠。（R8 返航生成点）
- **GIVEN** landed 状态，**WHEN** 玩家同时站在舱门和舵轮的 anchor_radius 覆盖区域内，**THEN** 两个站点均为 `ready`，焦点系统按优先级和距离选择唯一焦点——两者可独立交互、互不干扰。（R4）
- **GIVEN** 任一站点处于 `ready`，**WHEN** 玩家执行 Use 且领域系统返回 `UseLocked`，**THEN** 该站点状态变为 `busy`；交互完成后返回 `ready`。（R2 站点状态机）
- **GIVEN** landed 状态且玩家在舱门或舵轮 anchor_radius 内，**WHEN** 按 Use，**THEN** 确认对话框包含：整备站点检查清单（标注已访问/未访问状态）、航线风险评级、货舱剩余容量、模块完好度摘要。所有项目可带警告，但不阻断确认按钮。（R9）
- **GIVEN** 玩家从未访问任何整备站点，**WHEN** 直接走到舱门按 Use，**THEN** 确认对话框列出情报台/伙伴驻点/货舱均为"未访问"状态并显示提示文本及对应后果（情报台→遭遇率+10%、伙伴→无侦察简报、货舱→容量"未确认"、模块→效率95%），但确认按钮始终可点击。（R9 软机械后果）
- **GIVEN** 玩家访问了情报台但未访问伙伴驻点，**WHEN** 在舱门按 Use，**THEN** 情报台显示"已读"且无遭遇率惩罚，伙伴驻点显示"未交互"并附带"无侦察简报"后果，两者以不同视觉层级呈现（已访问=正常 / 未访问=警告图标+后果文本）。（R9 部分整备）

**公式覆盖：**

- **GIVEN** cargo_module 已安装在模块接口 B，**WHEN** 调用 `room_exists(cargo_hold)`，**THEN** 返回 true。
- **GIVEN** cargo_module 未安装，**WHEN** 调用 `room_exists(cargo_hold)`，**THEN** 返回 false。
- **GIVEN** `base_lock_duration = 2.0s`，**WHEN** 玩家确认出航（无论 Mode A 还是 Mode B），**THEN** 确认时刻到场景切换的间隔 = 2.0s ± 0.1s。

**跨系统交互：**

- **GIVEN** 玩家选择 Mode A（舱门→航图）且无有效航线，**WHEN** 航图系统返回拒绝，**THEN** departure_locked → landed 回退，显示拒绝原因提示，移动恢复；舵轮（Mode B）仍可用。
- **GIVEN** 货舱 `used_volume > 0`，**WHEN** 玩家在模块接口尝试卸下 cargo_module，**THEN** 操作被拒，UI 显示"请先清空货舱"。
- **GIVEN** 模块槽 damaged 但 installed，**WHEN** 查询 `room_exists(cargo_hold)`，**THEN** 返回 true（舱室存在性只看安装不看完好度）。
- **GIVEN** cargo_module 已安装（货舱 `exists`）且货舱中有货物，**WHEN** 航行中模块被摧毁（`installed` → `empty`），返航 arrival 时，**THEN** 货舱内容按资源系统规则处理（部分损失 + 可回收货箱），货舱变为 `not_exists`（视觉缺口），维修点标出需修复槽位。（R6 完整生命周期）
- **GIVEN** 货舱模块被摧毁后，**WHEN** 玩家获取新模块并重新安装到对应槽位，**THEN** `room_exists(cargo_hold)` 重新变为 true，货舱重新拼装到船体上，可步行进入。（R6 重新安装）

**边缘情况：**

- **GIVEN** 一个包含 `docking_state = departure_locked` 的快照（模拟页内隐藏最高尝试保存捕获的瞬态，或手动构造的测试夹具），**WHEN** Hub 从此快照加载，**THEN** Hub 初始化为 `landed` 状态，生成点在舱门（安全默认），出航确认丢失，日志记录 "departure_locked 降级为 landed"。
- **GIVEN** 航图场景或自由飞行地图加载超时，**WHEN** departure_locked 中，**THEN** 保留 locked → 错误提示 → 恢复 landed。
- **GIVEN** `departure_lock_duration` 配置为 NaN 或 <1.0s 或 >5.0s，**WHEN** Hub 执行启动验证，**THEN** 配置被拒绝，使用默认值 2.0s，记录验证失败日志。
- **GIVEN** Hub 处于 departure_locked 且在 `departure_lock_duration * 3` 内动画未完成，**WHEN** 看门狗超时触发，**THEN** Hub 强制恢复为 landed，解除移动冻结，写入错误日志。

### 补充手动验证

以下定性要求无法被单条 GWT 完全捕获，归属 Visual/Feel 类型，通过截图 + lead sign-off 验证：

**R1 — 身体化验证：**
- QA 遍历整备流（生活舱→驾驶舱→工程舱→货舱→出航/舵轮），逐一确认每个交互步骤都发生在场景中而非 UI 面板跳转。
- QA 遍历返航流（舱门进入→货舱拆包→工程舱查看→生活舱休息），确认节奏感和归位感。

**R6 — 舱室门控视觉验证：**
- 截图确认货舱未安装时对应位置显示缺口/空白（不可步行进入）。
- 截图确认货舱模块安装后舱室拼装到船体上、可步行进入。
- 截图确认拼装动画 ~1-2s 传达"家在成长"。

**R7 — 痕迹锚点视觉验证：**
- 截图确认完成世界修复返航后，船体维修点出现新的修补痕迹标记。

**R9 — 确认对话框信息密度验证：**
- 截图确认出航确认对话框包含整备站点检查清单、航线风险评级、货舱容量、模块完好度摘要。
- 确认所有未访问站点以警告形式列出，但确认按钮始终可点击。

**整备流节奏验证：**
- QA 分别测试"完整整备流"和"直接出航"两条路径，确认前者有仪式满足感、后者不被卡住。

**状态指示灯可辨识性：**
- 确认模块槽指示灯（绿/黄/灭）在 1m 视距内可通过形状区分解读，色盲模式下仍有区分度。

**双层楼梯过渡：**
- 确认楼梯/梯子的视觉过渡（自动攀爬 vs 按键触发）不破坏空间连续感，相机过渡流畅。
