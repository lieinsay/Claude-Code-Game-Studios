## 第 1 章：Visual Identity Statement

《云海织航》的视觉身份是“航路修复主义”：每一帧都必须像一个正在被修补、扩建、重新连通的飞艇与世界，所有造型、UI、色彩与信息层都优先服务“可读的连接与照料”，而不是炫技式装饰。

### Supporting Visual Principles

#### 1.1 修补痕迹优先

任何场景、角色、设施或载具，只要承担修复、扩建、维护、加固、补给的叙事功能，就必须把这些状态直接画出来。补丁、绑带、编号、临时支架、替换件、磨损边缘、不同材质拼接，都是画面语言的一部分。

- **Serves Pillars**: 规划先于冒险；世界会回应照料；飞艇是家，不只是载具。
- **Design Test**: 如果去掉修补痕迹后，画面仍像完整、静态、无维护压力的成品世界，这个设计不合格。

#### 1.2 航标化信息层

路线、资源、风险、任务、交互节点都要像航图和航标一样被组织。用线、点、环、标记、刻度、色带和局部高亮表达状态，让 UI 像“可被阅读的地图”，而不是浮在地图上的菜单。

- **Serves Pillars**: 规划先于冒险；未知带来温和压力。
- **Design Test**: 玩家判断“去哪、走哪条线、哪里危险、哪里可交互”时，信息必须在 1 秒内可读。

#### 1.3 家园感高于展陈感

飞艇内部、村镇室内、伙伴活动区必须像有人长期生活、整理、修理、积累的地方，而不是展览厅或纯功能面板。空间允许局部拥挤、挂靠、分区、收纳与个人痕迹，但整体必须有秩序、有归属感、有安全边界。

- **Serves Pillars**: 飞艇是家，不只是载具；少量深关系胜过大量收集；世界会回应照料。
- **Design Test**: 如果一个室内空间更像展示间、仓库或机库，而不是可居住的家，就需要增加使用痕迹、收纳逻辑和角色个性物件。

### Style Is Not

- 不做高饱和、强金属光泽、炫技型蒸汽朋克或重工业奇观。
- 不依赖 3D 高保真材质堆细节。
- 不做纯装饰性的奇幻天空童话。
- 不做脏乱失控的废土风格。
- 不把 UI、地图和世界强行分离成三套视觉语言。

## 第 2 章：Mood & Atmosphere

本章的情绪系统遵循同一条底层规则：所有状态都必须保留“可被看懂、可被修补、可被带回家”的感觉。即使进入高风险或失败状态，也不能把画面推向纯粹压迫式表现，而要让玩家始终读到航路、损伤、补救与返航的可能性。

情绪切换主要通过色温倾向、对比密度、光源组织、信息层拥挤度、粒子节奏来完成，而不是单纯依赖画面变暗或变亮。

### 2.1 飞艇内部 / 整备状态

- **情绪目标**: 这里不是停靠的交通工具，而是正在被持续照料的移动家园。氛围应安定、专注、可协作，带有工作台与居住舱并存的亲密感。
- **光照 / 色温 / 对比度**: 中低亮度、低到中等对比。主光源来自舱顶灯、壁灯、仪表面板和舷窗漏入的环境光，整体为中性灰白 + 琥珀点光。2D 表现使用柔和顶部渐变、局部高亮描边、低幅度阴影和少量发光仪表。
- **氛围关键词**: 整备、缝补、秩序、呼吸感、协作。
- **能量级别**: 低能量，持续准备态。
- **承载元素**: 半打开检修面板、外露管线、补丁位置、工具架、绑带、零件盒、挂钩、低频摆动吊灯、表盘、缆绳、布帘、桌面航线记事和手写批注。

### 2.2 安全航线 / 普通航行

- **情绪目标**: 前进是可控的，世界暂时愿意配合。它不是高亢冒险，而是平稳、可信、带方向感的移动体验。
- **光照 / 色温 / 对比度**: 高可读、中等亮度、中等偏低对比。环境基调偏冷青 / 纱蓝，飞艇本体与导航信息用少量琥珀与象牙白点亮，形成环境偏冷、人工信息偏亮的分层。
- **氛围关键词**: 航迹清楚、节拍稳定、视野开阔、风感轻、可靠。
- **能量级别**: 中低能量，匀速推进。
- **承载元素**: 稳定航迹线、航标点、风向标记、缓慢滚动云海、远景层、微摆缆绳和旗布、稳定闪烁的导航 UI、路径高亮、云隙反光。

### 2.3 未知或高风险航线

- **情绪目标**: 压力上升但不是绝望。核心不是可怕，而是信息不足、风险上升、必须保持连接。画面要提示玩家读图、控速、保留返航余量。
- **光照 / 色温 / 对比度**: 压缩色域、偏冷底色、局部高对比警示。背景降低饱和度，危险信息用冷蓝、青白、警示橙和红色脉冲点状跳出。
- **氛围关键词**: 预警、压缩、读图、逼近、未定。
- **能量级别**: 中高能量，但必须可控。
- **承载元素**: 异常云团、风切纹、云海裂缝、紊流边缘、扫描线、雷达圈、警示三角、路径断点、短促闪烁航标灯、仪表抖动、漂浮碎屑。

### 2.4 小型探索 / 搜撤场景

- **情绪目标**: 这是一次边找边带回去的任务，而不是清图。氛围应谨慎、专注、带轻微发现感，让玩家进入搜寻、确认、收纳、搬运的工作状态。
- **光照 / 色温 / 对比度**: 局部照明明显、背景较平、目标高可见。环境底层略灰化或轻度去饱和，关键可交互物、搜撤目标和路径提示必须明确高亮。
- **氛围关键词**: 搜寻、贴地、回收、断续光、专注。
- **能量级别**: 中等偏低，注意力集中。
- **承载元素**: 散落货箱、碎件、缆线、残片、可回收标识、地面痕迹、踩踏路径、手绘箭记、临时标记旗、交互闪点、轮廓描边、收纳网和回收袋。

### 2.5 修复成功 / 世界回应

- **情绪目标**: 投入被看见了。修复不是孤立动作，而是让网络重新运作，让空间重新说话。情绪包含释放、确认和被世界回馈的轻微喜悦。
- **光照 / 色温 / 对比度**: 亮度短暂抬升、色彩恢复、对比先收后放。修复点先高亮闪烁，再向外扩散成线路回流；被修复区域从灰化逐步回到原本配色。
- **氛围关键词**: 复通、回响、脉冲、确认、被看见。
- **能量级别**: 短促高点，随后快速回落到稳定。
- **承载元素**: 重新点亮的航标、线路、节点、修复后发亮的接缝和供能纹路、扩散粒子、环形波纹、线网回流、NPC 或环境物件同步变化、地图上重新连通的路径。

### 2.6 起始空港 / 村镇

- **情绪目标**: 这是有人照料、允许停靠、愿意提供补给与信息的起点。它应有前线生活区的质地，而不是旅游景点。
- **光照 / 色温 / 对比度**: 开放环境光 + 局部庇护区强化。外围是自然天空光和环境漫反射，中心节点如商铺、修理棚、公告板、集会处使用更明亮的人工照明或棚下暖色局部光。
- **氛围关键词**: 停靠、坊市、交接、人声、前线日常。
- **能量级别**: 中低能量，社交活跃。
- **承载元素**: 码头缆桩、停泊索、货架、修理棚、公告栏、村镇屋檐、布幔、旗帜、灯绳、路牌、交易桌、储物架、饮水点、等候长椅、航线传单。

### 2.7 失败或带损返航

- **情绪目标**: 局势吃紧，但仍然有机会把船带回去。这不是惩罚式破坏，而是受损后的勉力维持。损坏必须可见，可修复路径也必须可见。
- **光照 / 色温 / 对比度**: 整体饱和度下降、关键系统高对比报警、局部故障闪烁。画面底层偏灰冷，损伤区域用断续火花、漏光、烟尘和异常阴影强调；导航、返航箭头和生命线信息保持高对比可读。
- **氛围关键词**: 紧急、裂痕、维持、滴漏、勉强归航。
- **能量级别**: 高能量但收束感强。
- **承载元素**: 受损舱壁、裂纹、烟痕、漏气/漏能特效、抖动表盘、红色警报灯、闪断面板、临时绑扎、补强板、受损地图边缘、返航路线高亮、最低限度稳定照明。

### 2.8 主菜单 / 航图界面

- **情绪目标**: 玩家在进入游戏前就进入规划先于冒险的思维状态。主菜单与航图界面应像可操作的工作台式航路总图，安静、清晰、带有档案感和决策感。
- **光照 / 色温 / 对比度**: 低噪声背景、清晰高亮节点、层级分明的纸图 / 档案光感。背景可使用轻微纹理化云海地图、舱内桌面或折叠航图，整体亮度稳定。
- **氛围关键词**: 规划、档案、低噪、航路编排、选择清晰。
- **能量级别**: 低能量，思考优先。
- **承载元素**: 航图分层、线路节点、可选目标点、风险标记、折叠地图、桌面、标尺、标签、印章、批注、微弱节点闪烁、路线呼吸灯、舰船剪影、补给状态提示。

### 2.9 Chapter Rule

修补痕迹是秩序的一部分，航标化信息层是安全感的来源，家园感是所有情绪的归宿。任何后续美术、UI、特效和场景设计，只要出现“看不懂、回不去、感受不到正在被照料”的情况，都应优先回到本章重新校准。

## 第 3 章：Shape Language

形状语言是《云海织航》最先被玩家读懂的一层信息。它不只是“好看”，而是把航路修复主义翻译成一眼可辨的几何秩序：哪里能住、哪里能修、哪里在等待连通、哪里意味着风险。

在本作中，形状必须优先传达三件事：

1. **可读的连接**: 所有重要物体都应呈现被接上、可接上、正在接上的结构感。
2. **可照料的家感**: 轮廓要有保护性、容纳性，而不是纯展示性的锋利夸张。
3. **可导航的秩序**: 玩家在俯视地图、飞艇剖面、UI 和探索场景里，都应能靠形状直接判断功能与状态。

### 3.1 角色与伙伴剪影哲学

角色剪影的核心原则是：先读身份，再读关系，最后读情绪。角色不靠复杂细节取胜，而是靠轮廓差异、重心差异、连接件差异建立识别度。

- **玩家角色**: 稳定基础形 + 可修补的外接结构。主体轮廓清晰、可居住，边缘允许少量非对称挂件、绑带、工具、包袋和修补件，暗示其是能行动的维修者。情绪信息是可靠、可托付、能把事情一点点接回正轨。
- **伙伴**: 保留单一强记忆点，例如更高的头饰、更短更圆的体块、明显悬挂件、独特尾端或机械外接。伙伴剪影要更“被陪伴”，而不是更戏剧化。
- **普通 NPC**: 体块更朴素，外轮廓贴近地方生活功能。用围裙、背篓、工具带、补丁衣片、肩扛件表达职业与居住状态，但不能抢主角焦点。
- **危险单位**: 在剪影上打断连接感。它们可以尖、碎、偏移、断续、外突，但不能只是更华丽。危险感来自“形状不愿被安放”，而非单纯变大或变黑。

缩略图可读性规则：

- 角色缩略图必须保留头部、肩部、手部动作方向和一个识别附属件。
- 头身比例不靠夸张卖萌，而靠清晰分组；头部、躯干、挂件三段式最稳定。
- 轮廓内部细节不超过 2 到 3 个视觉焦点，避免 Web 小尺寸下糊成一团。
- 每个角色至少有一个连接物特征：工具钩、绑带、修补布、通讯线、符号吊牌、绑扎梁等。

区分法则：

- **玩家**: 最完整、最有组织感。
- **伙伴**: 最有单一记忆点。
- **NPC**: 最贴生活功能。
- **危险单位**: 最不连续、最难安放。

### 3.2 飞艇与舱室形状

飞艇的核心原则是：像一个能住、能修、能继续飞的身体。它必须同时满足三种视觉任务：

1. **横版剖面可步行**: 内部空间要能被读成可以穿行的居住结构。
2. **可修补**: 外壳必须允许出现可见补丁、加固梁、外接管路、临时支撑。
3. **可整备**: 系统组件应有明确模块边界，像能拆、能换、能扩建。

主体几何：

- 主壳体以长椭圆、船体弧线、胶囊形、拱腹型为主，传达容纳和承载。
- 结构骨架以横梁、肋骨、分段舱体、节点环为主。骨架不要隐藏，必须显露在形状层面，让玩家知道这不是装饰，而是可修的骨架。
- 扩建部分以侧挂模块、外接箱体、桥接廊、绑带式平台为主。新增内容应被看成后来接上的，而不是本体炫耀式膨胀。

舱室形状规则：

- **居住舱**: 圆角矩形、半拱门、低天花弧线，强调停留和安全。
- **工作舱**: 长方模块与外露管线，强调工具感和流程感，但仍保持可通行。
- **导航 / 核心舱**: 形状更集中、节点更明确，可用环形或束状结构突出路由中心。
- **补修区域**: 允许临时不对称、斜撑、布帘遮挡和外接脚手形状，让玩家读到正在修。

情绪信息：

- 稳定弧面 = 可以回家。
- 明确骨架 = 可以修。
- 模块化外接 = 可以继续长。

### 3.3 空港与村镇环境几何

空港和村镇的核心原则是：地方文化不是装饰风格，而是修法的差异。每个聚落都应体现地方文化、修复状态和居住痕迹。

- **空港**: 几何更明确，平台、坡道、吊臂、信标塔、绳桩、停靠环等元素形成导向结构。空港的形状重心偏向连接和调度。
- **村镇**: 几何更分散，更重视围合、过渡和生活边界。房屋不必整齐对齐，但要彼此有连接路径、补接结构、遮雨挑檐和共享平台。

地方文化的几何差异应表现为如何连接，而不是多么繁复：

- 绳索与悬挂式连接：轻巧、灵活。
- 木梁与斜撑：扎实、耐久。
- 环形停靠与围合庭院：适合聚集与协作。

修复状态的形状表达：

- **完好**: 构造连续、路径顺畅、边界清楚。
- **轻损**: 局部补板、临时扎带、替代支架。
- **重损**: 可见断裂、外撑结构、布罩遮挡、替代通道。
- **重连中**: 桥接段、导向标、临时路径、半成品加固件。

居住痕迹应以“占据边角但不封死通路”的方式出现。居住不是杂乱堆满，而是空间被温柔地长期使用。

### 3.4 航线、地图与 UI 的形状语法

航线、地图和 UI 不能只追求未来感，而要像一套可持续使用的航标系统：明确、可修正、可补记、可追踪。形状语法要服务“看得懂”和“回得去”。

**线的语法**

- **实线**: 已确认、已连通、可依赖的路径。
- **虚线 / 断续线**: 未确认、临时、受损或待修复路径。
- **双线 / 加粗线**: 主航路、关键连接、优先级高的线路。
- **带节点的线**: 可以中停、补给或切换的路段。

**点的语法**

- 点代表站点、节点、标记、事件或信标。
- 点的大小反映功能层级，不随机闪烁。
- 空心点表示可到达但未启用；实心点表示已确认可用；叠加环线的点表示当前关注目标。

**环的语法**

- 环代表可达范围、修复进度、影响区、信号范围或保护区。
- 环越完整，越像被照料、被稳定下来的区域。
- 破碎环表示联系被切断或仍在修补。

**标记与箭头**

- 箭头只用于方向明确的任务、航行、修复推进，不用于纯装饰。
- 标记形状应带有航标、挂签、封条、索引卡感，而不是游戏化爆炸特效感。
- 重要标记要像被人亲手挂上去的，不像系统随机弹出的。

**警示形状**

- 危险警示优先用尖角、楔形、断裂三角、偏移叉形。
- 警示形状不应过度战斗化，而要像航路被扰乱的提醒。
- 警示不是炫耀冲突，而是提示这里需要判断、可能需要修补。

### 3.5 Hero Shapes vs Supporting Shapes

**Hero shapes** 是让玩家知道“这很重要”的形状。它们必须面积足够大、轮廓稳定、含义明确。适合做 hero shape 的对象包括玩家角色主体、飞艇主舱与核心节点、主要任务标记、关键航标与主航路、重要伙伴的单一记忆点。

**Supporting shapes** 的任务是补足叙事和功能，但不争夺视线。它们包括次要装置、结构加固件、背景建筑、地面纹理块面、普通道具和环境挂件、辅助指示符。Supporting shapes 应更小、对比更低、边缘张力更少、识别特征更少。

视觉层级原则：

- 先看 hero shape，再看 supporting shape。
- 先读“能去哪里、能修什么、谁在等我”，再读背景装饰。
- 如果 supporting shape 抢过 hero shape 的注意力，它的轮廓、对比或尺寸超标。

### 3.6 明确禁止的形状倾向

- **纯炫技的尖锐高密度细节**: 过多锐角、齿状边、复杂碎片会破坏可修补的家感。
- **完全对称、无痕迹的工业洁净体**: 过于完美、无补丁、无接缝、无外接痕迹，会让世界显得不可接近。
- **只追求可爱或只追求酷的单向极端**: 本作需要可亲近但不幼态、可紧张但不绝望。
- **过度装饰化的空心轮廓**: 装饰必须服从结构，不得抢过结构。
- **大量无层次的碎片堆叠**: 不适合 2D Web 的缩略显示，会让阅读成本升高。
- **断绝连接、无法推测用途的异形体**: 形状必须暗示入口、支撑、接口或用途。

### 3.7 Chapter Rule

《云海织航》的形状语言不是更复杂，而是更会说明事情。所有形状都要讲清楚：这不是一片等待征服的天空，而是一个正在被修好、被安顿、被带回家的世界。

## 第 4 章：Color System

颜色在本作中不是装饰层，而是信息层的一部分。它必须同时完成三件事：让玩家一眼分辨哪里能走、哪里能修、哪里有风险；让飞艇与世界看起来像被长期照料过的真实空间；在小尺寸 Web-first 2D 画面里保持清晰可读。

本作的颜色逻辑遵循航路修复主义：

- 颜色优先服务连接、修补与导航，而不是炫目展示。
- 基础色来自材料本身，信号色来自灯塔、标识、警告与关键资源。
- 不同地区可以有地方性强调色，但必须服从整体修补语法与生活气息。

### 4.1 Primary Palette

| 名称 | 建议 Hex | 角色 / 含义 | 使用场景 |
| --- | --- | --- | --- |
| 航雾海蓝 | `#5E7F8B` | 远海、天空阴影、冷风与距离感；代表外部世界与未完全抵达之处。 | 船体阴影、远景天幕、地图边缘、低优先级信息背景。 |
| 雾灰白 | `#D8DAD4` | 海雾、纸面、图纸、未知轮廓；不是空白，而是尚未被命名。 | 主界面底色、地图底板、未确认区域、说明文本底层。 |
| 帆布米 | `#E4D2B3` | 帆布、床铺、缝补布片、手工照料感；让空间有被住着的温度。 | 舱内墙面、家具、UI 面板、修复后的中性高亮。 |
| 旧木褐 | `#8A694D` | 船梁、扶手、木箱、耐用结构；强调手工建造和长期使用痕迹。 | 结构边框、木质设备、地板、港口与居住空间。 |
| 氧化铜绿 | `#6F8E87` | 氧化后的金属、管线、铆钉与旧机械外壳；说明机器被持续维护。 | 机械件、接口框、设备边沿、工业构件、次级导视。 |
| 路线金 | `#C8A34E` | 航线、关键资源、修复后的关键连接；价值来自秩序与路径。 | 航线、核心资源、重要标记、成功修复提示、主航图线条。 |
| 航标青 | `#4FB7B2` | 灯塔信号、可交互节点、可通行路径与可信连接。 | 交互高亮、可用状态、导航点、活跃指示、信息引导。 |

蓝只负责距离、阴影和空气感，不承担全部信息。生活色由帆布米、旧木褐和氧化铜绿承担；功能色由路线金与航标青承担。所有主色都偏低饱和，保证浏览器压缩显示、小图标和缩放界面中稳定。

### 4.2 Semantic Colors

| 状态 | 建议色 | 语义含义 | 世界里的理由 | 备份方式 |
| --- | --- | --- | --- | --- |
| 危险 | `#C8644B` 警戒锈红 | 紧急、受威胁、不要继续靠近。 | 像过热金属、锈蚀和急促信号灯，属于出事时刻。 | 断裂三角、楔形切角、闪烁频率、急促音效。 |
| 安全 / 可用 | `#4FB7B2` 航标青 | 可操作、可通行、可确认。 | 像灯塔和信号灯，对应这里有连接、可以信任。 | 圆环、锚点、实心小点、轻微脉冲。 |
| 奖励 / 关键资源 | `#C8A34E` 路线金 | 重要、稀缺、值得优先处理。 | 金色代表能把系统重新接起来的价值，而不是奢华。 | 星点、加粗线框、收束动画、确认音。 |
| 已修复 | `#E8DCC0` 补缝帆白 | 已完成、已恢复、连接重新建立。 | 修复后应像被照料过，而不是换成全新物件。 | 线缝、补丁边、短暂暖光收束、柔和完成音。 |
| 未确认 / 未知 | `#D8DAD4` 雾灰白 | 尚未探明、未命名、信息不足。 | 未知是还没被记录进图纸的空白，不是黑洞。 | 虚线边框、问号式节点、低频漂浮动效、轻微噪点。 |
| 受损 / 失败 | `#7A7068` 暗损灰褐 | 失效、破裂、不可用、需要处理。 | 失败是结构疲劳、断缝、脱落与失联，不是爆炸式戏剧化。 | 裂纹、偏移描边、断续抖动、低沉故障音。 |

语义色使用原则：

- 危险色只用于真正需要立即回避的内容。
- 路线金只用于关键路径、核心资源和重要确认。
- 航标青只用于可以交互、可以前进、可以信任的对象。
- 已修复必须呈现被缝回去的感觉，而不是换成全新物件的感觉。

### 4.3 Area and State Temperature Rules

- **飞艇内部**: 暖中性，底色以帆布米、旧木褐、氧化铜绿为主。航雾海蓝只用于窗外、投影和阴影。
- **安全航线**: 冷静、清透、低饱和。背景用雾灰白和航雾海蓝，线路与节点用路线金与航标青。
- **高风险航线**: 亮度下降、对比上升、色相收紧。增加暗损灰褐和警戒锈红，路线金只保留为极少量导向提示。
- **探索点**: 初见时偏未知色，确认后逐步转入航标青或路线金。探索过程就是从雾中被标记出来。
- **修复成功**: 色温回升，帆布米与路线金占比增加，断裂边缘柔化为完整线条。
- **空港村镇**: 允许地方性强调色，但必须建立在本地材料与生产习惯上。
- **带损返航**: 降饱和、偏灰、偏暗，局部保留路线金和警戒锈红作为还能返航但已受损的提示。
- **主菜单 / 航图**: 底色接近雾灰白与帆布米，线条接近路线金与航标青，材质纹理更轻。

地方性强调色规则：

- 每个村镇、伙伴阵营或局部地区只能有一个主强调色。
- 强调色只占少量面积，常出现在旗帜、绣边、陶器、标识牌、发带、徽章和局部 UI 标签上。
- 强调色必须来自本地材料或生产习惯，例如陶土红、苔绿、海洗青、灰靛、麦秆黄等。

### 4.4 UI Color Rules

UI 必须和世界共享同一套语义逻辑，但不能直接复制世界的材质表现。

- **一致性**: UI 与世界共享路线金、航标青、雾灰白、帆布米这四个核心信息色。
- **分离性**: 世界色偏材质、光照和磨损；UI 色偏扁平、清晰和信息化。UI 不使用过多纹理，不依赖环境阴影。
- **底层处理**: 常驻 UI 面板优先使用雾灰白与帆布米，辅以旧木褐或氧化铜绿边框，避免纯黑大面积底色。
- **层级处理**: 文本、数值和按钮状态必须先靠明度层级区分，再靠色相区分。颜色只做第二层信息。
- **交互处理**: 可点、可拖、可确认的元素统一使用航标青或路线金，但二者必须通过图标和轮廓形状区分用途。
- **移动与提示**: UI 动效只用于状态变化，不用于持续炫耀。颜色变化应短促、明确、可中断。

### 4.5 Colorblind Safety

本作不能依赖纯色相差来完成关键信息传达，尤其是 Web-first 2D 中的小图标、狭窄状态条和地图节点。

- **危险锈红**: 可能与旧木褐、暗损灰褐接近，必须叠加断裂三角、楔形切角、脉冲频率和警示音。
- **安全航标青**: 可能与氧化金属色接近，必须叠加圆环、锚点或实心节点。
- **路线金**: 小尺寸下可能与帆布米、雾灰白接近，必须叠加加粗线型、星点、双层描边或收束动画。
- **未确认 / 未知**: 不能只靠更淡的灰区分，必须有虚线、噪点、问号式符号或半透明遮罩。
- **已修复**: 不能只靠变亮表达，必须有缝线、补丁边和完成动效。
- **受损 / 失败**: 不能只靠变暗表达，必须有裂纹、错位、抖动或破损轮廓。

硬性要求：

- 任何 24px 以下的状态图标，必须同时拥有颜色、形状和边缘特征三层辨识。
- 任何关键资源或风险状态，不能只通过文本说明；必须有图标或轮廓辅助。
- 任何地图节点在缩小后仍应能靠点、环、三角、断线区分，而不是只靠色相。

### 4.6 Forbidden Color Usage

- 禁止整套高饱和蓝紫或霓虹蓝作为世界主色。
- 禁止把路线金、航标青、警戒锈红同时大面积铺满同一画面。
- 禁止把危险色当作装饰点缀，或把装饰色当作危险提示。
- 禁止所有地区使用同一个地方性强调色。
- 禁止使用纯白与纯黑作为大面积主界面底色。
- 禁止依赖颜色单独表达可交互、可通行、已完成、已损坏等状态。
- 禁止在小尺寸元素上使用低对比邻近色，例如帆布米对雾灰白、旧木褐对暗损灰褐、路线金对浅米色。

### 4.7 Chapter Rule

本作的颜色系统不是漂亮的配色表，而是航路与照料的可视化协议。玩家应当通过颜色直接感受到：哪里是家、哪里能修、哪里能走、哪里值得警惕、哪里还没有被命名。

## 第 5 章：Character Design Direction

角色设计必须服务于本项目的三层阅读顺序：**先读身份，再读关系，最后读情绪**。

在《云海织航》中，角色不是被展示的造型，而是“被修补的航路秩序”在人体尺度上的映射。所有人物都应让玩家一眼看出：他/她与飞艇、航线、维护、连接和归属的关系是什么。

### 5.1 角色总原则

1. **修补痕迹优先**
   - 角色的服装、装备与配件应呈现被使用、被缝补、被替换、被加固的状态。
   - 允许不对称、补丁、缝线、外接扣件、替换件、手工加固的金属片或帆布片。
   - 角色越重要，越不应显得崭新整洁，而应显得维护得很好。

2. **航标化信息层**
   - 角色身上的信息必须像航标一样工作：有明确方向性、识别性和功能性。
   - 标志、绶带、肩扣、腰挂、臂章、工具包、绳结、色带，都应承担识别身份、职能或关系的作用。
   - 装饰不可脱离功能；没有功能的花纹不应成为主视觉。

3. **家园感高于展陈感**
   - 角色不能像博物馆展品或纯视觉奇观，而要像能在飞艇上共同生活的人。
   - 面料偏实用，层次偏生活化，材质偏柔韧和可修补。
   - 角色的好看来自可长期共处，不是来自惊艳一次。

4. **小尺寸优先**
   - 在桌面浏览器的常用视距下，角色轮廓必须先于细节成立。
   - 每个角色的识别重心控制在 **2-3 个视觉焦点以内**。
   - 当缩小到角色头像或半身远视图时，仍要能读出职业、归属、关系倾向。

### 5.2 玩家角色视觉原型

玩家是 **维修者 / 航线开拓者 / 飞艇主人** 三重身份的合并体。视觉上要同时传达会修、会看、会决定。

#### 5.2.1 视觉关键词

- **工具性**
- **路径感**
- **掌舵感**
- **可依靠**
- **带着手工痕迹的组织者**

#### 5.2.2 造型结构

玩家角色应采用“**中轴稳定、外缘可扩展**”的结构：

- **中轴稳定**：头部、上身、腰带、工具挂载形成清晰主轮廓，读起来像中心人物。
- **外缘可扩展**：披肩、短披风、背挂地图筒、测线器、线轴、吊钩、护具等可形成外部功能层，像可以随任务增加或替换的模块。
- 不要让玩家角色过于轻飘或过于武装化。他/她不是军官，也不是冒险者模板，而是把世界重新接起来的人。

#### 5.2.3 身份表达

- **维修者**
  - 袖口、膝部、肘部有耐磨补强。
  - 携带小型工具袋、螺钉盒、缝补针包、扳手、胶片、铆钉串、临时封片。
  - 服装表面可见局部修补痕迹，强调自己也在维护系统。

- **航线开拓者**
  - 身上有路线记录与方向识别元素：折叠地图、航标旗片、针盘、绳结编码、路线色带。
  - 上身可以有更明显的纵向指引线，暗示带路的人。
  - 外挂件应有轻微风向感，形成总在看向前方的姿态逻辑。

- **飞艇主人**
  - 视觉上要有能管理空间的秩序感：腰封、肩带、工具分区、挂载位置清晰。
  - 不追求贵气，而追求有归属权、能做决定、能照看他人的稳定气质。
  - 可保留一处更私人的标记：自制徽章、旧钥匙、舱门编号牌、家族或船名织标，作为这艘船属于谁的锚点。

#### 5.2.4 推荐轮廓

- 上半身略强于下半身，体现行动与决策中心在手和胸口。
- 一处明显的挂载重心应落在身体一侧，形成实用感而非对称礼装感。
- 头肩之间不宜过于宽大战斗化，避免将玩家误读为前线战士。
- 轮廓应像随时可以停下修东西的人，而不是随时准备冲锋的人。

#### 5.2.5 玩家角色禁忌

- 不要把玩家做成纯英雄式、纯学院式、纯军装式。
- 不要出现夸张大披风、大剑、大体积武装导致职业误读。
- 不要把“主人”表现为奢华贵族；应表现为责任在身的组织者。

### 5.3 伙伴 / 船员方向

首发伙伴只有一个功能动词：**侦察**。

伙伴设计必须做到两件事：

1. 让玩家立刻知道他/她负责看前方、看边缘、看危险。
2. 让这位伙伴成为玩家关系中最清晰、最单一、最可记忆的一条纽带。

#### 5.3.1 伙伴的设计目标

- **单一功能动词清晰**
  - 视觉上要体现看、探、先一步发现的职责。
  - 服装与配件围绕视野、远距观察、标记路线展开。

- **少量深关系**
  - 伙伴不需要复杂职业叠加，不要兼具太多职能。
  - 伙伴的视觉记忆点应服务于你会依赖谁去确认前方。
  - 这个角色必须能和玩家形成稳定的双人关系结构：一个负责决定，一个负责先看见。

#### 5.3.2 侦察伙伴的造型逻辑

可选视觉资源应围绕观测展开，而不是战斗展开：

- 单筒望远镜、折叠镜片、挂耳镜、风向绳、小旗标、记号粉、轻型探杆。
- 外衣可以更轻、更灵活，便于爬舱、探边、靠栏、趴望。
- 轮廓上可增加一个独特的头部或肩部识别点，例如高立的帽檐、斜挂的镜带、单侧肩架、背后短旗杆。

#### 5.3.3 深关系的视觉表达

伙伴和玩家之间的关系，不应靠台词堆出来，而应靠视觉分工体现：

- 玩家身上偏组织、修复、掌舵。
- 伙伴身上偏先看、先标、先提醒。
- 两人并置时，玩家轮廓更稳定，伙伴轮廓更轻、更偏斜、更有方向性。
- 伙伴的动作多为前伸、侧望、回指、标注，形成与玩家下判断、落工具、修补的对照。

#### 5.3.4 伙伴的记忆点规则

- 只能有 **一个主要记忆点**，例如镜片、旗带、帽型、肩部装置、独特配色点。
- 记忆点必须和侦察功能直接相关。
- 不要同时给伙伴太多象征物，否则会失去单一功能动词的清晰度。

### 5.4 空港 / 村镇 NPC 方向

NPC 的任务不是显得特别，而是让玩家读到：**这个地方是怎么生活的，靠什么谋生，与航路有什么关系。**

#### 5.4.1 职业先行

NPC 必须先读出职业，再读地方性，最后才是情绪。

- 船坞工、缆绳工、补帆匠、码头记录员、货单员、茶水铺主、零件修理员、风向看守、灯塔值守者、杂货摊主等，都应有明确职业轮廓。
- 职业识别应来自工具、围裙、袖口磨损、绑带方式、肩背负重习惯，而不是仅靠台词说明。

#### 5.4.2 地方性表达

地方性不是民俗装饰堆砌，而是生活方式的痕迹：

- 靠海、靠港、靠风、靠修补的地方，衣着会更偏防潮、便携、可卷起、可套穿。
- 居民的颜色应比玩家更生活化，更偏雾灰、帆布米、旧木褐、氧化铜绿的混合使用。
- 地方纹样应来自功能：编号、结绳、网格、封签、边角补强，不要无意义的大图案。

#### 5.4.3 生活痕迹表达

NPC 的服装和身体状态应透露长期劳动与地域习惯：

- 袖口发白、膝部补片、围裙污渍、绳结磨痕、背包压痕、护手磨损。
- 可出现局部统一的地方识别元素，如港口袖标、区段编号、集市织带、镇上通用的封签颜色。
- NPC 的整体视觉应完整但不精致，让玩家感到这个地方真实运转。

#### 5.4.4 NPC 的群体区分

同类 NPC 之间要能迅速区分职业和区域：

- 通过帽型、肩部线条、腰挂工具、围裙长度、腿部绑带和背负方式区分。
- 不同年龄层可以通过重心变化体现：年轻者更轻、更快、更偏向外出；年长者更稳、更垂、更有储物感。
- 群体中可以有少量个人物件，但不应破坏职业归属的清晰度。

#### 5.4.5 NPC 禁忌

- 不要让空港村镇 NPC 过度奇幻化、贵族化、异域化。
- 不要把每个 NPC 都做成独立主角感，否则群体环境会失真。
- 不要给 NPC 无意义的大面积发光或复杂装甲；那会削弱生活场景可信度。

### 5.5 危险单位 / 环境威胁方向

本项目中的危险，不应主要表现为战斗敌人，而应表现为**连接被破坏**。

危险单位或环境威胁的视觉核心不是攻击性，而是系统失联、结构松脱、路径断裂、航标失准。

#### 5.5.1 危险表达原则

- 危险单位要显得不连续、不稳定、难以安放。
- 它们应像原本属于系统，但现在已经偏离：断线、错位、反向、扭曲、侵蚀、污染、漂移。
- 视觉上应让人感觉它不是完整生命体，而是被破坏后的连接残影。

#### 5.5.2 造型语言

危险单位可使用以下方向：

- **断裂结构**：部位之间不完全连接，边缘像被撕开或拆卸。
- **异步运动**：身体局部运动节奏不同步，显得不协调。
- **错误拼接**：像临时拼合、旧件错装、规格不匹配。
- **残缺轮廓**：主轮廓缺少闭合，存在空洞、断口、漂浮碎片。
- **污染边界**：不是纯粹恶意，而像连接被腐蚀后溢出的失控状态。

#### 5.5.3 色彩使用

- 危险锈红只用于真正风险。
- 不能把所有威胁都染成红色，避免失去警示价值。
- 威胁可更多依赖阴影偏移、氧化铜绿污染、暗雾、破损金属反光、异常闪烁、线路错接等方式表达。
- 真正危机时再引入锈红作为最后一级警报。

#### 5.5.4 环境威胁的优先方向

比起怪物感，更应突出：

- 断缆
- 漏风
- 裂隙
- 失衡
- 堵塞
- 逆流
- 失航
- 失联

这些威胁可以以环境物、装置异常、半有机故障体、错误连接体等方式出现，但都要避免直接转入传统战斗怪物模板。

#### 5.5.5 危险单位禁忌

- 不要做成纯尖刺怪、纯恶魔、纯野兽的通用战斗模板。
- 不要把危险单位设计得过于完整、工整或帅气。
- 不要使用过度鲜艳的红黑攻势造型，否则会把连接被破坏的主题拉成泛战斗风格。

### 5.6 表情、姿态、动画风格

本项目为 Web 2D，动画必须在有限成本下提供足够的情绪辨识和功能反馈。动画不追求高帧数的炫技，而追求动作语义清楚。

#### 5.6.1 表情风格

- 表情应偏 **克制、可读、可复用**。
- 面部结构建议保留清晰的眉眼区、嘴部轮廓与眼神方向，便于小尺寸识别。
- 表情变化优先通过眉形、眼睑开合、口型开闭、头部倾角、肩部紧张度来传达。

#### 5.6.2 姿态风格

角色姿态应体现有任务的人在船上生活：

- 玩家：稳、可停、可修、可看远处，重心略前但不前冲。
- 伙伴：轻、快、侧向多、常有半转身和探头动作。
- NPC：因职业而异，但普遍存在劳动姿态和停靠姿态。
- 危险单位：不稳定、偏斜、错位、不可预测。

#### 5.6.3 动画节奏

- 主角动画应有工具动作循环与待机呼吸循环两类基础节奏。
- 伙伴动画应更强调观察动作和提示动作。
- NPC 动画应低频、重复、符合生活状态，避免抢镜。
- 危险单位动画可采用不对称循环、错拍节奏、断续抖动、局部滞后，以强化失联感。

#### 5.6.4 动画技术执行建议

- 以 2D 骨骼或分层切片动画为主，保证可维护性。
- 大动作尽量拆成清楚的阶段：起势、执行、回收。
- 表情替换与手部替换要适配浏览器性能。
- 每个角色至少准备：待机、交互、强调/提示、受挫/警示、轻情绪变化五类基础表现。

#### 5.6.5 不推荐的动画风格

- 过度夸张的卡通弹跳，不符合修补航路的真实劳动感。
- 过度写实的复杂肌肉运动，不适合 Web 2D 成本。
- 全角色统一同一种活泼大动作会破坏身份层级。

### 5.7 LOD / 游戏镜头距离规则

角色设计必须从一开始就考虑远近可读性。本项目的镜头和尺寸变化较大，因此角色需要按以下层级设计。

#### 5.7.1 远距层

适用于地图视图、俯视探索、航线界面、小头像：

- 只保留 **轮廓、头型、职业标记、1 个主色块、1 个功能识别点**。
- 远距层不可依赖细碎纹理或复杂小物件。
- 角色一旦缩小，仍必须能读出这是玩家、伙伴、NPC 或危险。

#### 5.7.2 中距层

适用于横版剖面行走时的常规镜头：

- 保留服装层次、工具挂载、肩腰关系、明显补丁和材质分区。
- 允许少量装饰，但必须服务于身份和关系。
- 中距层是本项目最关键的实际工作层，所有主动作都应在这一层稳定成立。

#### 5.7.3 近距层

适用于对话、特写、重要交互、UI 内角色展示：

- 可显示更多面部表情、手部细节、服装修补细节、个人物件。
- 但近距层也不能和中距层脱节；近看只是补充信息，不是完全换一个造型逻辑。

#### 5.7.4 LOD 规则

- 每个角色必须提前确认：远距时靠什么识别，中距时靠什么建立关系，近距时靠什么补充情感。
- 如果某个设计只在近距成立，说明它不适合本项目。
- 如果某个设计在远距已经过度复杂，也不适合本项目。

### 5.8 角色分类执行规则

#### 5.8.1 玩家

- 视觉中心最完整、最有组织感。
- 修补痕迹是能干的证据，不是破旧的证据。
- 所有功能都围绕维护航路与家园展开。

#### 5.8.2 伙伴

- 只有一个核心功能动词。
- 记忆点少而准，关系感要强。
- 与玩家形成明显的功能互补。

#### 5.8.3 NPC

- 先读职业，再读地方。
- 生活痕迹先于审美风格。
- 群体要构成一座能运转的空港或村镇。

#### 5.8.4 危险单位 / 环境威胁

- 不连续、错位、难安放。
- 表达连接破坏，而非传统战斗炫技。
- 红色只在真正危险时使用。

### 5.9 禁止角色设计倾向

以下方向在本项目中应明确禁止：

1. **纯战斗化设计**
   - 大量盔甲、武器、尖刺、杀气化轮廓会偏离主题。
   - 本项目不是战斗英雄集合，而是航路修补共同体。

2. **泛奇幻模板化**
   - 精灵化、魔导师化、骑士化、盗贼化等现成模板会削弱世界的航运与维护感。

3. **过度精致与无痕化**
   - 没有修补、没有磨损、没有工具痕迹的角色不成立。

4. **信息过载**
   - 单个角色的小尺寸焦点超过 3 个，视读就会失效。

5. **危险红泛滥**
   - 锈红必须保留警报权威，不能滥用。

6. **纯展示性造型**
   - 只适合立绘、不适合行走、不适合交互的设计，不可作为主角或常驻角色方案。

7. **情绪先行、身份模糊**
   - 角色不能先让人觉得可爱、帅或酷，而看不出他是谁、负责什么、和谁有关。

### 5.10 本章落地标准

当任何角色设计稿完成时，必须通过以下检查：

- 3 秒内能否读出身份？
- 是否能看出与玩家的关系？
- 是否能看出此角色在世界中的功能？
- 是否保留了修补痕迹与生活痕迹？
- 在缩小到游戏常用尺寸后，轮廓是否仍然成立？
- 是否避免了战斗化、模板化、展陈化？

如果其中任一项回答不清楚，说明设计还未达到本项目标准。

## 第 6 章：Environment Design Language

环境设计必须让玩家读到三件事：**这里如何连接、这里如何生活、这里如何被修复**。

《云海织航》的环境不是风景背景，也不是传统地牢集合。每个空间都应像航路网络中的一个可维护节点：有停靠方式、有使用痕迹、有损坏状态、有修复后的回应。环境越重要，越不能只靠奇观成立，而要靠“我能理解它怎么运转”成立。

### 6.1 环境总原则

1. **连接先于装饰**
   - 场景中的桥、绳、缆、管、路、平台、信标、标牌、舱门，都必须先说明连接关系。
   - 装饰元素必须服务路径、职业、地方习惯或修复状态。
   - 玩家进入新环境时，应先读到可走路线、可停靠点、可交互节点和风险边界。

2. **生活痕迹先于奇观**
   - 村镇、空港和飞艇内部都必须显得被长期使用，而不是刚摆好的舞台。
   - 晾晒、堆放、修补、临时加固、工具归位、搬运路径，都是环境可信度的核心。
   - 奇观只允许作为远景或重要节点存在，不能压过场景的使用逻辑。

3. **损坏必须可诊断**
   - 破损不能只是“变脏、变暗、变碎”，必须让玩家看出哪里断了、哪里漏了、哪里堵了、哪里失联了。
   - 环境威胁应表现为连接问题：断缆、漏风、裂隙、失衡、逆流、堵塞、航标失准。
   - 如果玩家无法从画面理解问题类型，就不能支撑修复玩法。

4. **修复必须留下痕迹**
   - 修好不是恢复成全新，而是出现新的补片、缝线、支架、标牌、航灯和通行线。
   - 修复后的环境应更清楚、更安全、更有人气，但仍保留被照料过的材料历史。
   - 世界回应要可见：灯亮、路线回流、NPC 动线改变、摊位重开、平台重新可达。

### 6.2 飞艇内部环境

飞艇内部是玩家的家、工作台、仓库、路线决策室和出航前整备场。它必须在横版剖面里同时保持可读、可住、可修。

#### 6.2.1 空间结构

- 舱室采用横向串联为主，局部上下层作为扩展。
- 每个舱室应有明确功能：驾驶/航图、居住、仓储、工坊、能源、伙伴休息、货物整理。
- 舱门、梯子、扶手、地板边缘和平台必须稳定表达可通行范围。
- 不使用过多纯装饰隔断；每个隔断最好承担承重、收纳、遮挡、管线或安全边界作用。

#### 6.2.2 材料与细节

- 主材料：帆布、旧木、氧化金属、绳索、铆钉、补强皮革、半透明舷窗。
- 可见结构：肋骨梁、外露管线、挂载轨、维修盖板、模块接缝。
- 生活细节：床铺、杯具、地图批注、挂衣钩、工具架、修补布卷、备件箱。
- 细节要沿使用路径分布，不要平均铺满画面。

#### 6.2.3 模块升级表现

飞艇成长不应表现为“变豪华”，而应表现为“更能承担旅程”：

- 新模块像后来接上去的舱段，有接缝、临时支架、外露固定点。
- 升级前后要保留同一结构来源，让玩家感到这是自己的船在变好。
- 高级模块可以更整洁、更稳定，但不能变成无痕科技设备。
- 每次功能解锁都应伴随一个可见环境变化，例如新工作台、新地图层、新仓储位、新航灯。

#### 6.2.4 飞艇禁忌

- 禁止把飞艇做成纯军舰、纯豪宅或纯科幻控制室。
- 禁止所有舱室用同一套材质和同一亮度，导致功能无法区分。
- 禁止用大量不可交互的复杂机械遮挡玩家路径。

### 6.3 云海与航线环境

云海不是普通天空背景，而是世界的“地面”。它承载距离、未知、风险和路线感。

#### 6.3.1 云海层级

- **远景层**：大面积雾灰白、航雾海蓝、远处浮陆和海面反光，负责世界尺度。
- **中景层**：云带、风向纹、漂浮残骸、远处航标、岛屿轮廓，负责路线判断。
- **近景层**：船体边缘、缆绳、风压粒子、短距障碍和可交互航标，负责行动反馈。

三层必须各司其职，不能让背景细节抢走路线节点和危险提示。

#### 6.3.2 航线视觉元素

- 已知航线：连续线、稳定航标、清晰节点、低频光脉冲。
- 未知航线：虚线、雾遮、残缺节点、局部扫描、被风带切断的线段。
- 高风险航线：路径边缘破碎、风切纹增强、航标偏移、可见返航余量提示。
- 修复航线：断点被补线接回，航标从闪断变成稳定发光。

#### 6.3.3 浮空陆地与海面

- 浮空陆地必须有“为什么能被停靠”的边缘结构：码头、吊台、根系状岩层、旧锚点、缆桩、风向标。
- 海面作为世界底层，应更多出现在远景、阴影和垂直尺度提示中，避免抢占主要活动层。
- 浮陆边缘应保留坠落感和风蚀感，但不要做成单纯危险悬崖；它首先是被人使用过的地方。

### 6.4 空港与村镇环境

空港和村镇是玩家反哺世界的主要可见对象。它们必须像会被居民重新使用的地方，而不是一次性关卡。

#### 6.4.1 空港结构

- 空港优先使用平台、坡道、吊臂、停泊环、灯塔、信号旗、货架和修理棚。
- 停靠路线必须清楚：飞艇从哪里来、在哪里固定、货物怎么搬、居民如何上下。
- 空港中心应有一个可记忆节点，例如灯塔、公告塔、集市棚、主缆桩或航图墙。

#### 6.4.2 村镇结构

- 村镇更强调围合、过渡和生活边界：屋檐、连廊、共享平台、晾晒区、手作棚、储物角。
- 建筑不需要完全整齐，但路径必须能被读懂。
- 每个村镇应有一种主要连接方式，例如绳索悬挂、木梁斜撑、环形平台、帆布廊道或阶梯停靠。

#### 6.4.3 地方差异

地方差异来自“如何生活与修补”，不是随机换色：

- 渔网式聚落：更多网格、挂绳、轻型平台、晾晒结构。
- 木梁式聚落：更多斜撑、宽台、厚门框、旧木补强。
- 灯塔式聚落：更多竖向信标、环形栏杆、光源层级、观察台。
- 市集式聚落：更多摊棚、布幔、货架、封签、路线告示。

每个地方可以有一个强调色，但必须从当地材料和生产习惯中来。

#### 6.4.4 修复回应

同一地点至少需要三种状态：

- **破损态**：路径断、灯不稳、货物停滞、人少、遮挡多。
- **临修态**：出现脚手架、临时绳桥、补强板、施工标记、待搬材料。
- **复通态**：灯稳定、路线清晰、居民活动恢复、摊位或功能重新开放。

状态切换应改变空间动线，而不只是改变颜色。

### 6.5 探索点与搜撤小副本

小副本是“失联系统残段”，不是传统地下城。它的美术重点是让玩家判断：什么值得拿、哪里有风险、怎么撤回去。

#### 6.5.1 场景类型

- 漂浮残骸：破舱、断梁、旧货箱、失效航标、被云雾半埋的结构。
- 失联平台：停摆机械、断缆、废弃补给点、旧路线标记。
- 云海裂隙：风切、逆流、能见度断层、漂浮碎件。
- 废弃空港角落：封闭仓库、倒塌棚架、未取回货物、旧公告板。

#### 6.5.2 搜索视觉规则

- 可搜索物必须有稳定的轮廓和轻微信息提示，不能完全藏在噪声里。
- 高价值物和普通物通过形状、位置和保护结构区分，不只靠发光。
- 可撤离方向必须始终存在视觉线索，例如绳索、风向旗、返航标、临时灯。
- 危险区域应先通过环境语法预告，再造成损失；避免无提示惩罚。

#### 6.5.3 压力表达

搜撤压力来自信息不足和携带选择，不来自强限时压迫：

- 画面可逐步增加雾、风、抖动、断续光、路径遮挡。
- UI 与环境共同提示风险升高，但不能让玩家失去判断能力。
- 撤离成功时，应强调“带回了能改变世界的东西”，而不仅是战利品入包。

### 6.6 环境交互与可读性

所有环境元素按功能分为四类：可通行、可交互、危险、叙事装饰。

#### 6.6.1 可通行

- 使用稳定平台、连续边线、扶手、路灯、地面磨损和人流痕迹表达。
- 可通行边缘不能和纯背景结构混淆。
- 横版剖面中，地面和梯子必须优先于装饰纹理被读到。

#### 6.6.2 可交互

- 使用航标青、路线金、挂签、工具轮廓、轻微脉冲或局部描边。
- 可交互元素必须有功能理由，例如需要修、可开、可查、可搬、可标记。
- 不允许全场景到处闪光，避免交互语义失效。

#### 6.6.3 危险

- 使用断裂三角、偏移边缘、错位运动、警戒锈红、异常音和局部抖动。
- 危险提示必须在接触前出现。
- 危险区域可以紧张，但必须保持逃离路径可读。

#### 6.6.4 叙事装饰

- 叙事装饰只补充生活、历史和地方性，不承担核心玩法判断。
- 装饰密度应避开玩家路径、交互节点和危险边界。
- 背景故事物件必须能解释“谁在这里生活过、修过、等待过”。

### 6.7 前景 / 中景 / 背景职责

#### 6.7.1 前景

- 用于遮挡、深度、临近感和少量动态气氛。
- 前景不能长时间挡住角色、路径、交互物和 UI。
- 前景运动要慢、少、轻，除非正在表达明确风险。

#### 6.7.2 中景

- 是主要玩法层，承载角色、路径、互动、危险和关键物件。
- 中景对比度最高，边缘最清楚。
- 所有玩法判断优先在中景成立。

#### 6.7.3 背景

- 承载世界尺度、远景浮陆、云海、海面、航线延伸和地方氛围。
- 背景色彩和细节必须低于中景。
- 背景可以暗示未来可达区域，但不能假装成当前可交互对象。

### 6.8 环境状态表

| 状态 | 视觉表现 | 玩家感受 | 设计目的 |
|---|---|---|---|
| 未知 | 雾遮、虚线、低对比轮廓、未命名标记 | 想确认，但不被强迫 | 支撑探索欲 |
| 可用 | 稳定边线、航标青、清楚路径、轻脉冲 | 可以靠近 | 支撑规划 |
| 受损 | 裂缝、断缆、暗损灰褐、局部锈红 | 需要处理 | 支撑修复目标 |
| 临修 | 脚手、补板、临时绳桥、施工标记 | 正在变好 | 支撑世界回应 |
| 复通 | 灯稳、路径连贯、居民回流、路线金回路 | 投入被看见 | 支撑长期成长 |
| 高危 | 风切、抖动、警示形状、可撤离线索 | 谨慎但能判断 | 支撑搜撤压力 |

### 6.9 禁止环境设计倾向

- 禁止把环境做成只适合截图、不适合导航的背景画。
- 禁止用纯黑暗、纯迷雾或纯遮挡制造不可读压力。
- 禁止每个村镇只换颜色、不换生活方式和连接方式。
- 禁止把修复表现成全新替换，抹掉原有材料历史。
- 禁止把搜撤点做成传统战斗地牢，忽视搜索、回收和撤离。
- 禁止让装饰物抢过路径、危险和交互节点。
- 禁止使用无功能来源的大面积魔法发光或科技光污染。

### 6.10 本章落地标准

任何环境设计稿必须通过以下检查：

- 玩家 3 秒内能否读出主要路径？
- 玩家能否区分可通行、可交互、危险和装饰？
- 场景是否说明了这里如何停靠、居住或工作？
- 损坏是否可诊断，而不是只变脏变暗？
- 修复后是否留下新的痕迹和世界回应？
- 地方差异是否来自生活方式，而不是随机换色？
- 在 Web 2D 常用视距下，中景玩法层是否足够清楚？

如果环境不能回答这些问题，它就还没有服务“航路修复主义”。

## 第 7 章：UI / HUD Visual Direction

UI 不是脱离世界的科技面板，而是玩家在世界中使用的 **航图、挂签、修补记录、航标系统和舱内仪表** 的可操作版本。

《云海织航》的 UI 必须让玩家持续处在“规划、确认、修补、返航”的思维里。它应当清晰、安静、可信，像一套长期被使用的航行工作台，而不是一层浮在游戏上的华丽游戏皮肤。

### 7.1 UI 总原则

1. **规划先于刺激**
   - UI 的第一职责是帮助玩家判断路线、风险、资源、状态和下一步行动。
   - 不使用大面积炫光、强弹窗、过度动效抢夺注意力。
   - 所有界面都要让玩家感到“我能做计划”，而不是“系统在催我”。

2. **世界语义一致**
   - UI 继承世界中的航标、挂签、封条、补片、图纸、绳结、仪表、路线线段等视觉语法。
   - UI 可以更规整、更清晰，但不能变成与世界无关的纯现代玻璃面板。
   - 每个 UI 元素都应有像世界物件一样的功能来源。

3. **小尺寸可读优先**
   - Web-first 2D 要优先考虑浏览器窗口、缩放、低分辨率和长时间阅读。
   - 关键信息必须通过颜色、形状、图标、边缘和文本多层表达。
   - 任何 24px 以下图标不能只靠颜色区分。

4. **信息有安静层级**
   - 常驻信息应低噪声，临时警示才提高对比和动效。
   - 信息优先级应稳定：生存/返航 > 当前路线 > 风险 > 资源 > 世界回应 > 装饰。
   - UI 不应把每个数值都做成同等重要。

### 7.2 UI 视觉隐喻

本作 UI 的主要隐喻是 **航行工作台**。

它由以下材料和形状构成：

- 航图纸面、半透明描图层、坐标网格。
- 挂签、封条、编号牌、手写批注、路线夹。
- 仪表盘、指针、灯点、机械开关、标尺。
- 补片边、缝线、铆钉、纸胶带、临时修正线。
- 航标节点、信号环、虚线航路、断裂警示形。

UI 应像被船员长期使用、不断修正的工具，而不是一次性展示板。

### 7.3 全局 HUD

全局 HUD 承载玩家在探索、航行和舱内活动时的最低必要信息。它必须轻、稳、可隐藏，不能压住 2D 画面主体。

#### 7.3.1 常驻信息

常驻 HUD 只保留最关键内容：

- 当前地点 / 航线状态。
- 飞艇核心状态：耐久、能源、载重或关键补给。
- 当前目标或最近可执行动作。
- 返航或安全线索。
- 少量伙伴提示入口。

不推荐常驻显示过多数值、任务列表或满屏资源条。资源和细节信息应收纳到航图、仓储或整备界面中。

#### 7.3.2 HUD 位置

- 左上：当前地点、航线或任务上下文。
- 右上：轻量系统入口，例如航图、日志、设置。
- 左下：飞艇状态或角色即时状态。
- 右下：当前可用动作、工具、交互提示。
- 屏幕中心只用于短促反馈，不承载长期面板。

实际布局可根据原型调整，但必须保持“边缘承载、中心留给世界”的原则。

#### 7.3.3 HUD 造型

- 面板优先使用薄边框、浅底色、轻纹理，不使用厚重卡片堆叠。
- 形状以标签、窄条、圆环节点、短面板为主。
- 常驻 HUD 的边缘应像挂在航图或仪表上的标签，而不是现代系统浮窗。
- 重要状态可用补丁形、封条形或航标环强化。

### 7.4 航图与路线规划界面

航图是本作最重要的 UI 类型。它必须让“开放世界探索”和“规划先于冒险”同时成立。

#### 7.4.1 航图结构

- 底层：云海、浮陆轮廓、坐标网格、未确认雾区。
- 中层：航线、节点、风险区、补给点、可停靠点。
- 上层：当前计划、目标路线、返航线、任务挂签、修复进度。

玩家应能一眼区分：

- 已确认路线。
- 未知路线。
- 高风险路线。
- 已修复路线。
- 当前选择路线。

#### 7.4.2 路线语法

- 实线：已确认、可依赖。
- 虚线：未知、临时、待确认。
- 断线：受损、不可稳定通行。
- 双线：主航道或高价值路线。
- 带环节点：可停靠、可补给、可交互。
- 破碎环节点：失联、待修复或高风险。

所有路线状态都必须同时依靠线型、节点形状和颜色，不只依靠颜色。

#### 7.4.3 路线规划反馈

选择路线时，界面应反馈：

- 预计风险。
- 所需补给或关键条件。
- 可能收益类型。
- 返航难度。
- 是否能反哺某个地点或系统。

反馈方式应像航图批注，而不是弹出一堆战斗数值。高风险信息必须清楚，但不要制造硬性限时压力。

#### 7.4.4 航图禁忌

- 禁止把航图做成纯开放世界清单面板。
- 禁止所有点都同样发光，导致主目标和普通信息混淆。
- 禁止只用问号堆满地图，削弱世界可信度。
- 禁止让奖励信息压过路线、风险和返航判断。

### 7.5 飞艇整备界面

整备界面是玩家发展自身、管理飞艇、准备下一次出航的核心界面。它应该像舱内工作台，而不是抽象升级菜单。

#### 7.5.1 模块表现

- 飞艇模块应以剖面舱室、挂载区、修补面板或结构图形式呈现。
- 每个模块有明确位置、功能和状态。
- 升级不是单纯数值增长，而应显示新部件、新接缝、新工具位或新功能标识。
- 受损模块要能看出故障类型，例如裂缝、漏能、堵塞、松脱、失准。

#### 7.5.2 资源与制作

资源图标必须与世界材料一致：

- 帆布、绳索、木材、金属片、航灯件、图纸、旧零件、修补胶、信标芯。
- 图标采用清晰轮廓和少量材质特征，不做过度写实小图。
- 稀有资源可以使用路线金，但面积必须小，避免所有材料都像奖励。

制作与修理界面应强调“材料去向”：

- 哪个部件被修。
- 哪条航线会受益。
- 哪个村镇功能会恢复。
- 哪个风险会降低。

#### 7.5.3 伙伴与舱内关系

伙伴界面不做大量角色收集册，而做少量深关系记录：

- 伙伴当前职责。
- 与飞艇模块或航线的关系。
- 可触发的协助动作。
- 关系记忆或重要事件。

视觉上应像船员记录卡、手写备注、任务分工牌，而不是抽卡角色详情页。

### 7.6 搜撤界面

搜撤场景 UI 的任务是让玩家判断：还能拿什么、风险多高、是否该撤。

#### 7.6.1 常驻搜撤信息

搜撤 HUD 至少表达：

- 当前携带量。
- 关键回收物。
- 风险等级。
- 撤离方向或撤离条件。
- 飞艇/角色当前受损状态。

信息必须清晰但克制。搜撤压力来自判断与取舍，不来自 UI 持续尖叫。

#### 7.6.2 背包与携带表现

- 背包格不应做成纯通用网格，建议像货袋、收纳网、绑带槽、货架区。
- 物品大小、重量或风险可以通过形状和边缘处理表达。
- 高价值回收物应显得“有用”，例如带接口、编号、补片价值或航线标记，而不只是发光宝物。

#### 7.6.3 风险提示

- 风险升高使用短促动效、边缘警示、航标闪断、仪表抖动。
- 警戒锈红只在真正危险阶段出现。
- 撤离线索必须在 UI 和环境中同时存在：UI 给方向，环境给路径。

#### 7.6.4 成功撤离反馈

撤离成功不只显示获得物品，而应显示：

- 带回了什么材料。
- 哪个飞艇模块可修。
- 哪条航线或哪个村镇可被反哺。
- 新增了什么情报或地图确认。

这类反馈应连接到世界回应，而不是停留在战利品结算。

### 7.7 世界回应与修复反馈 UI

修复反馈是本作长期动力的重要视觉证明。

#### 7.7.1 修复前后对比

修复 UI 应用简洁的前后状态展示：

- 断线 -> 连线。
- 暗灯 -> 稳定灯点。
- 破碎环 -> 完整环。
- 空白区域 -> 命名节点。
- 停摆功能 -> 可用功能。

对比不应像成就弹窗，而应像航图记录被补完。

#### 7.7.2 影响范围显示

每次重要修复都应显示影响范围：

- 影响哪个村镇。
- 开通哪条航线。
- 降低哪类风险。
- 解锁哪个补给、伙伴互动或探索方向。

影响范围优先用地图线、节点环、标签和短批注表达。

#### 7.7.3 情绪节奏

修复反馈可以短暂提高亮度与动效，但必须快速回归安静状态。

- 第一拍：修复点亮。
- 第二拍：路线回流。
- 第三拍：影响标签出现。
- 第四拍：状态稳定入档。

这样能让玩家感到世界回应，而不是被奖励动画打断。

### 7.8 图标系统

图标必须像航行系统的一部分，不能像随机游戏图标包。

#### 7.8.1 图标形状来源

- 航线：线、点、环、箭、断口。
- 修复：补片、针脚、扳手、铆钉、封条。
- 风险：断裂三角、楔形切角、错位叉、破碎环。
- 资源：材料轮廓、接口、捆扎、编号。
- 伙伴：职责符号、船员牌、观察镜、工具标。

#### 7.8.2 图标规则

- 每个图标优先依靠大轮廓识别。
- 小尺寸图标只保留 1 个主形状和 1 个辅助特征。
- 图标线宽要统一，避免有的像手绘、有的像现代扁平 UI。
- 图标可带轻微手工感，但不能影响清晰度。

#### 7.8.3 禁止图标倾向

- 禁止无来源的魔法符号。
- 禁止过度细碎的写实图标。
- 禁止每种资源都做成同样的圆形徽章。
- 禁止只靠颜色区分状态图标。

### 7.9 字体、文本与数字表现

UI 文本应服务扫描，不做装饰性阅读负担。

#### 7.9.1 字体方向

- 中文界面优先使用清晰、现代、可长时间阅读的无衬线字体。
- 标题可轻微增加图纸或航行记录感，但不能降低识别。
- 数字、资源量、风险值必须对齐稳定，避免跳动影响判断。

#### 7.9.2 文本层级

- 大标题只用于界面名、地点名、重大修复结果。
- 常驻 HUD 使用小而清晰的标签文字。
- 解释文本应短，像航图批注，不写长篇说明。
- 关键按钮文本必须直接表达动作，例如“设为航线”“开始整备”“标记撤离”。

#### 7.9.3 文本禁忌

- 禁止在 UI 内用大段文字解释本该由图形表达的状态。
- 禁止把所有按钮做成同等尺寸和同等强调。
- 禁止为了氛围使用难读字体。

### 7.10 响应式与 Web 约束

本作首发为 Web 桌面浏览器，UI 必须适配常见窗口尺寸和缩放行为。

- 所有核心面板要支持 16:9、16:10 和较窄桌面窗口。
- 重要按钮和图标必须有稳定点击区域，不依赖像素级精确操作。
- 面板不应靠屏幕边缘硬贴死，应保留安全边距。
- 长列表要有分页、折叠或分类，不能无限向下堆。
- 常驻 HUD 在窗口缩小时应优先隐藏次级信息，而不是压缩到不可读。
- 所有关键状态必须在 100% 浏览器缩放下可读。

### 7.11 UI 动效

UI 动效只用于表达状态变化、确认和风险，不用于持续装饰。

#### 7.11.1 推荐动效

- 路线点亮：线段顺序回流。
- 节点确认：短促环形收束。
- 修复完成：补片边缘亮起后稳定。
- 风险升高：断续脉冲、边缘偏移、仪表短抖。
- 资源入库：物件轻微落位到货架或收纳槽。

#### 7.11.2 动效节奏

- 普通确认：短、轻、稳定。
- 重要修复：短暂高点后收束。
- 风险警示：频率高但范围小。
- 长期状态：尽量静态，避免视觉疲劳。

#### 7.11.3 禁止动效

- 禁止无状态变化的持续闪烁。
- 禁止满屏粒子奖励。
- 禁止让 UI 动效盖过角色动作和环境判断。
- 禁止无法中断的长动画阻塞玩家操作。

### 7.12 UI 可访问性规则

UI 必须默认照顾色盲、低分辨率和长时间游玩。

- 颜色必须配合形状、图标、线型或文本。
- 危险、可用、未知、已修复、受损必须有不同形状语法。
- 文本和底色保持足够明度对比。
- 字号不能为了氛围过小。
- 闪烁频率要克制，避免持续高频刺激。
- 键鼠操作路径必须清楚，hover、focus、pressed 状态都有明显反馈。
- 关键操作需要明确确认态，不能只靠颜色变化表示已选中。

### 7.13 禁止 UI 倾向

- 禁止把 UI 做成高饱和科幻蓝紫玻璃面板。
- 禁止所有元素都卡片化、浮窗化，导致世界和 UI 割裂。
- 禁止用大面积红色制造常驻压力。
- 禁止奖励结算压过世界修复结果。
- 禁止把航图做成纯任务列表。
- 禁止把整备做成只有数值和按钮的升级树。
- 禁止把搜撤 UI 做成高压限时竞技界面。
- 禁止用装饰纹理降低文本和图标可读性。

### 7.14 本章落地标准

任何 UI 设计稿必须通过以下检查：

- 玩家能否在 3 秒内读出当前最重要的行动？
- UI 是否看起来属于这个世界，而不是套在上面的现代皮肤？
- 航线、风险、资源、修复、撤离是否有稳定语义？
- 颜色是否都有形状、图标或线型备份？
- 常驻 HUD 是否足够克制，不遮挡世界？
- 整备和结算是否指向世界反哺，而不只是角色变强？
- 在浏览器常见尺寸下，文本和点击区域是否仍然可用？

如果 UI 不能帮助玩家规划、确认、修补和返航，它就偏离了本作的视觉身份。

## 第 8 章：Asset Production Standards

资产生产标准的目标是把“航路修复主义”转成可执行、可检查、可复用的制作规则。

本项目是 Web-first 2D 游戏，所有资产都必须优先满足：**小尺寸可读、浏览器性能可控、风格一致、后续可扩展、状态变化可维护**。任何资产如果只在单张大图里好看，却无法服务游戏镜头、交互状态和迭代制作，都不应进入正式资产库。

### 8.1 通用资产原则

1. **先定义用途，再制作细节**
   - 每个资产必须先说明它用于角色、环境、UI、航图、特效、动画还是图标。
   - 资产的尺寸、层级、颜色和命名都应由用途决定。
   - 不制作“可能以后会用”的无归属装饰资产。

2. **读法优先于细节**
   - 远看先读轮廓，中看读功能，近看读材料与情绪。
   - 小尺寸下无法识别的细节，不应成为资产核心。
   - 关键状态必须有颜色、形状、边缘或动效的备份。

3. **修补痕迹必须可复用**
   - 补片、缝线、铆钉、断线、裂纹、临时支架等元素应形成可复用资产组。
   - 修复状态不能靠重新画整套图解决，应尽量通过叠加层、替换件和状态变体实现。
   - 同类修补语言要统一，避免每个资产都像来自不同项目。

4. **性能是风格的一部分**
   - 浏览器端不能依赖过大纹理、过多透明叠层和高频粒子。
   - 动画帧数、图层数量和特效数量都要以可维护为前提。
   - 资产必须在常见桌面浏览器窗口内保持清晰和稳定。

### 8.2 文件命名规则

所有资产命名必须表达：类型、对象、状态、方向或版本。

推荐格式：

```text
<category>_<object>_<state>_<variant>_<size>
```

示例：

```text
char_player_idle_v01_mid
char_scout_prompt_v01_mid
env_airship_workshop_repaired_v01
env_port_lighthouse_damaged_v01
ui_icon_route_unknown_24
ui_panel_map_node_active_v01
fx_route_reconnect_pulse_v01
```

#### 8.2.1 Category 前缀

- `char`：角色、伙伴、NPC、危险单位。
- `env`：环境、建筑、场景物件、背景层。
- `ui`：界面面板、按钮、图标、航图组件。
- `fx`：特效、粒子、状态反馈。
- `anim`：动画片段、序列或可替换动作资源。
- `mat`：材质、纹理、图案、补片资源。

#### 8.2.2 State 状态词

常用状态词必须统一：

- `idle`：待机。
- `active`：可用或激活。
- `unknown`：未知。
- `damaged`：受损。
- `repairing`：临修中。
- `repaired`：已修复。
- `warning`：警示。
- `locked`：未解锁。
- `selected`：已选择。
- `disabled`：不可用。

禁止同一状态在不同文件中使用多套词，例如 `broken`、`hurt`、`bad` 混用。除非设计文档另有定义，统一使用上面的状态词。

### 8.3 尺寸与分辨率标准

具体尺寸可随原型调整，但必须遵循稳定档位，避免每个资产使用随机尺寸。

#### 8.3.1 UI 与图标

- 小图标：`24x24`，用于状态、小型资源、节点辅助标记。
- 标准图标：`32x32` 或 `48x48`，用于按钮、资源、航图节点。
- 大图标：`64x64` 或 `96x96`，用于结算、模块、重要资源。
- UI 面板优先使用可缩放九宫格、矢量式形状或可重用边框，而不是为每个尺寸单独绘制整张图。

#### 8.3.2 角色

- 常规游戏镜头角色以中距可读为准。
- 角色资产必须准备至少三类显示用途：地图/小头像、常规行走、对话或近距展示。
- 不允许只制作近距立绘而忽略游戏内小尺寸读法。

#### 8.3.3 环境

- 环境资产应按前景、中景、背景分组。
- 可交互环境物件必须独立切出，不能烘死在背景图里。
- 需要状态变化的物件必须有 `damaged`、`repairing`、`repaired` 或等价状态变体。

#### 8.3.4 特效

- 特效图集应保持小而集中，避免为单次反馈使用过大序列帧。
- 路线回流、节点点亮、修复收束等核心特效应优先做成可复用组件。
- 高频粒子必须有数量上限，并在浏览器中验证。

### 8.4 图层与源文件标准

源文件必须支持后续修改和动画拆分。

#### 8.4.1 角色源文件

角色源文件至少应分层：

- 头部。
- 躯干。
- 手臂与手部。
- 腿部。
- 主要工具或挂件。
- 表情替换层。
- 修补痕迹或状态叠加层。

如使用 2D 骨骼或分层切片动画，所有可动部位都必须清楚命名，不允许使用 `Layer 1`、`Group 2` 这类无意义名称。

#### 8.4.2 环境源文件

环境源文件至少应分层：

- 背景远景。
- 背景中景。
- 主要可通行层。
- 可交互物件。
- 危险或受损状态层。
- 修复状态层。
- 前景遮挡层。
- 光照与氛围层。

可交互、危险和修复状态不能完全合并进背景，必须能被程序或关卡编辑流程独立控制。

#### 8.4.3 UI 源文件

UI 源文件至少应分层：

- 背板。
- 边框。
- 图标。
- 文本占位。
- 状态叠加。
- hover / focus / selected / disabled 状态。

UI 资产必须能支持键鼠状态反馈，不能只提供静态默认图。

### 8.5 角色资产标准

#### 8.5.1 玩家角色

玩家角色至少需要：

- 待机。
- 行走。
- 交互。
- 修理。
- 查看航图或确认方向。
- 受挫/警示。
- 简短成功反馈。

玩家的修补工具、挂载重心、私人标记和中轴稳定结构必须在常规游戏尺寸下可见。

#### 8.5.2 侦察伙伴

侦察伙伴至少需要：

- 待机。
- 观察。
- 指示方向。
- 警示。
- 轻快移动。
- 关系互动或回应。

伙伴只能保留一个主要视觉记忆点，且必须与侦察功能有关。不能在制作阶段追加与功能无关的大量挂件。

#### 8.5.3 NPC

NPC 资产按职业制作，不按“漂亮程度”制作。

每个 NPC 至少应能读出：

- 职业。
- 所属地点或生活方式。
- 使用痕迹。
- 与航路、修补或空港活动的关系。

普通 NPC 不应拥有比玩家和核心伙伴更抢眼的主轮廓或信号色。

#### 8.5.4 危险单位

危险单位资产必须体现连接破坏：

- 断裂。
- 错位。
- 异步。
- 失联。
- 污染。
- 不稳定。

危险单位不能只靠尖刺、红黑配色或怪物脸表达威胁。

### 8.6 环境资产标准

#### 8.6.1 场景模块

环境模块应按用途拆分：

- 可通行平台。
- 梯子、坡道、扶手。
- 门、舱口、通道。
- 航标、信号灯、节点。
- 货架、箱包、修理棚、工作台。
- 断缆、裂缝、漏风口、堵塞物。
- 修复补片、临时支架、重连线。

模块必须能组合出破损态、临修态和复通态。

#### 8.6.2 背景资产

背景资产负责世界尺度，不负责核心交互。

- 远景浮陆、云海、海面、远处航标、大片雾区可合并处理。
- 背景对比度应低于中景玩法层。
- 背景中出现的可达区域必须通过航图或场景路径另行确认，不能误导玩家当前可交互。

#### 8.6.3 可交互物件

可交互物件必须独立、清楚、状态稳定。

- 默认态：低调但可识别。
- hover/focus：边缘或节点明确。
- active：航标青或路线金强化。
- disabled：降低对比并保留形状，不只变灰。
- repaired：增加补片、稳定灯或完整连接，而不是变成全新物体。

### 8.7 UI 与图标资产标准

#### 8.7.1 UI 面板

UI 面板分为：

- 常驻 HUD 面板。
- 航图面板。
- 整备面板。
- 搜撤背包面板。
- 修复反馈面板。
- 对话/伙伴记录面板。

每类面板必须共享边框、底色、状态色和图标语法，但可以通过形状比例区分用途。

#### 8.7.2 按钮状态

每个按钮至少提供：

- 默认。
- hover。
- focus。
- pressed。
- selected。
- disabled。

状态差异必须包含边缘、明度或形状变化，不能只改颜色。

#### 8.7.3 图标验收

每个图标必须通过三档检查：

- `24px`：能读出大类。
- `32px`：能读出功能。
- `48px+`：能读出材料或状态细节。

如果图标只在大尺寸下成立，应重新设计大轮廓。

### 8.8 动画资产标准

#### 8.8.1 动画节奏

动画以动作语义清楚为目标：

- 起势：让玩家知道动作开始。
- 执行：表达动作功能。
- 回收：返回可操作状态。

禁止让非核心动画过长，影响键鼠操作节奏。

#### 8.8.2 角色动画

角色动画优先使用 2D 骨骼或分层切片方式，减少重复绘制成本。

- 待机循环应低频。
- 交互动作应短而明确。
- 警示动作应比普通动作更快、更清楚。
- 情绪变化可通过头、肩、手和表情替换表达。

#### 8.8.3 环境动画

环境动画用于表达状态，而不是装饰：

- 航标灯稳定闪烁。
- 风带缓慢流动。
- 断线抖动。
- 修复线回流。
- 仪表指针偏移。
- 居民生活低频循环。

背景长期动画必须轻量，避免浏览器性能压力和视觉疲劳。

#### 8.8.4 UI 动画

UI 动画应短、明确、可中断：

- 普通确认：约短促一拍。
- 重要修复：点亮、回流、入档。
- 风险警示：小范围断续脉冲。
- 背包入库：物件落位到收纳槽。

禁止不可跳过或不可中断的长 UI 动画。

### 8.9 特效资产标准

特效要服务航路、修复、风险和反馈。

#### 8.9.1 推荐特效组

- 航线点亮。
- 节点确认。
- 修复收束。
- 断线闪烁。
- 航标脉冲。
- 漏风 / 漏能。
- 风切风险。
- 资源入库。
- 世界回应。

#### 8.9.2 特效颜色

- 航标青：可用、可信、可操作。
- 路线金：关键路径、修复回流、重要资源。
- 警戒锈红：真实危险。
- 雾灰白：未知、未确认、扫描。

特效不能把所有颜色同时叠加成高饱和噪声。

#### 8.9.3 特效禁忌

- 禁止满屏粒子奖励。
- 禁止持续大面积发光。
- 禁止用特效遮挡路径和交互物。
- 禁止把危险特效做成纯战斗爆炸。

### 8.10 导出与压缩规则

#### 8.10.1 导出格式

- UI、图标、角色切片、状态叠加：优先透明 PNG 或引擎推荐的无损/高质量格式。
- 大面积背景：可使用压缩纹理或适合 Web 的图片格式，但必须检查边缘和渐变质量。
- 图集：同类资产应合并图集，减少加载碎片。
- 临时草图和源文件不进入运行时目录。

#### 8.10.2 压缩检查

压缩后必须检查：

- 小图标边缘是否糊。
- 低饱和色是否变脏。
- UI 文本和线条是否出现压缩噪点。
- 渐变天空和云海是否出现明显色带。
- 透明边缘是否有白边、黑边或脏边。

#### 8.10.3 Web 性能约束

- 避免单张超大纹理承担过多信息。
- 避免大量半透明层持续覆盖全屏。
- 避免高频粒子长期存在。
- 避免为每个状态加载完全独立的大图。
- 优先复用模块、状态叠加和图集。

### 8.11 资产清单与元数据

每个正式资产应记录：

- 资产名。
- 类型。
- 使用场景。
- 状态变体。
- 尺寸。
- 是否可交互。
- 是否有动画。
- 是否有损坏/修复状态。
- 对应 GDD 或 Art Bible 章节。
- 当前状态：草稿、待审、通过、需返工、弃用。

资产进入制作前必须知道它服务哪个系统或场景。没有用途说明的资产不进入正式列表。

### 8.12 审核标准

每个资产交付时必须通过以下检查：

- 是否符合航路修复主义？
- 是否能在游戏常用尺寸下读清？
- 是否使用了正确的颜色语义？
- 是否有必要的状态变体？
- 是否保留修补、生活或连接痕迹？
- 是否和已有资产共享形状语言？
- 是否会误导玩家对路径、危险或交互的判断？
- 是否适合 Web 2D 性能预算？
- 文件名、图层名和导出格式是否规范？

任何一项不通过，应返工，不应靠后续实现阶段修补。

### 8.13 禁止资产生产倾向

- 禁止只做大图展示，不考虑游戏内尺寸。
- 禁止把所有资产都画成独立插画，无法模块化复用。
- 禁止用不同命名习惯混入同一资产库。
- 禁止将可交互物件烘死在背景里。
- 禁止没有状态变体的关键修复对象进入制作。
- 禁止图标只靠颜色表达状态。
- 禁止过度使用高饱和发光材质。
- 禁止为了省事让每个村镇共享同一套无地方差异资产。
- 禁止把浏览器性能问题留到后期集中处理。

### 8.14 本章落地标准

资产进入正式制作前，必须能回答：

- 它服务哪个玩法、场景或界面？
- 它在小尺寸下靠什么被识别？
- 它是否需要受损、临修、复通或其他状态？
- 它的颜色语义是否稳定？
- 它是否能被复用或模块化组合？
- 它是否适合 Web-first 2D 的性能约束？
- 它是否保留了连接、修补或生活痕迹？

不能回答这些问题的资产，不能进入正式生产。

## 第 9 章：Art Direction Governance

本章定义《云海织航》的美术方向治理规则。它的目的不是限制创作，而是保证后续角色、环境、UI、特效和资产扩展都不会偏离同一个视觉身份。

本项目的最高美术判断标准是：**任何画面都必须服务“航路修复主义”**。玩家看到它时，应能感到这个世界可以被理解、被照料、被重新连接，而不是被征服、被炫耀或被纯粹消费。

### 9.1 最高视觉原则

所有美术决策按以下优先级判断：

1. **可读性**
   - 玩家能否读出路径、身份、风险、交互和状态。
   - Web 2D 常用视距下是否仍然清楚。
   - 颜色、形状、线型、图标是否互相支撑。

2. **世界逻辑**
   - 资产是否解释了它如何被使用、维护、停靠、修补或记录。
   - 场景是否能说明居民如何生活、飞艇如何工作、航路如何连接。
   - 视觉差异是否来自功能和地方性，而不是随机换皮。

3. **情绪一致**
   - 画面是否保持可回家、可修复、可规划的底层气质。
   - 压力是否温和可判断，而不是硬压迫。
   - 成长是否表现为世界被照料，而不只是数值变强。

4. **生产可执行**
   - 资产是否能模块化、状态化、复用和维护。
   - 是否适合浏览器性能。
   - 是否能进入后续实现流程，而不是只适合静态展示。

当这四项冲突时，按以上顺序取舍。好看但不可读的方案不通过；漂亮但无法制作的方案不进入正式资产库。

### 9.2 Art Review 流程

所有正式资产都应经过以下阶段：

#### 9.2.1 概念草案

目的：确认方向是否符合 Art Bible。

检查：

- 是否服务航路修复主义。
- 是否能读出功能、关系或状态。
- 是否符合角色、环境、UI 或资产章节的对应规则。
- 是否存在明显的战斗化、模板化、过度奇观化倾向。

输出：

- `通过方向`
- `需调整后继续`
- `方向不适合，停止制作`

#### 9.2.2 游戏尺寸检查

目的：确认资产不是只在大图中成立。

检查：

- 缩小到游戏常用尺寸后是否仍能读出主轮廓。
- 24px、32px、48px 图标档位是否符合识别要求。
- 横版剖面中是否能区分角色、路径、交互和危险。
- 航图节点和 UI 状态是否有非颜色备份。

输出：

- `尺寸通过`
- `需要简化轮廓`
- `需要重建信息层级`

#### 9.2.3 状态变体检查

目的：确认资产支持玩法状态。

检查：

- 是否需要 `unknown`、`damaged`、`repairing`、`repaired`、`warning`、`active` 等状态。
- 状态之间是否只是变色，还是有形状、边缘、材质或动效变化。
- 修复后是否保留被照料过的痕迹。
- 受损状态是否能被诊断。

输出：

- `状态完整`
- `缺少状态变体`
- `状态语义不清，需要返工`

#### 9.2.4 实装前检查

目的：确认资产能进入 Godot Web-first 2D 流程。

检查：

- 命名、图层、尺寸、导出格式是否规范。
- 是否有不必要的大图、过多透明层或高频粒子。
- 可交互物是否独立切出。
- UI 是否包含 hover、focus、pressed、selected、disabled 状态。

输出：

- `可实装`
- `需技术美术调整`
- `需重新拆分资产`

### 9.3 通过 / 返工 / 禁止 标准

#### 9.3.1 通过

资产满足以下条件可进入正式库：

- 与航路修复主义一致。
- 小尺寸可读。
- 功能和状态清楚。
- 颜色语义正确。
- 文件命名、图层、导出规范。
- 不误导路径、危险、交互和资源判断。
- 能支持 Web 2D 性能要求。

#### 9.3.2 返工

出现以下问题，应返工而不是勉强接收：

- 轮廓在游戏尺寸下不清楚。
- 交互、危险、资源、路径互相混淆。
- 只靠颜色表达关键状态。
- 修复态像全新替换，缺少补痕。
- 地方差异只靠换色，不靠生活方式。
- 角色先读到“酷/可爱/华丽”，但读不出身份和功能。
- UI 像套在游戏外的现代皮肤。
- 特效抢过玩法判断。

#### 9.3.3 禁止

出现以下问题，应直接否决方向：

- 纯战斗英雄化、军械化、竞技化，压过修复和照料主题。
- 高饱和蓝紫霓虹或红黑攻击性风格成为主视觉。
- 资产无法在游戏中使用，只适合概念展示。
- 关键玩法对象被烘死在背景里，无法交互或变状态。
- 大量不可读装饰破坏路径、风险和 UI 清晰度。
- 用纯黑暗、纯遮挡、纯迷雾制造不可判断压力。
- 把世界成长表现为奢华升级，而不是功能复通和生活恢复。

### 9.4 扩展地区规则

后续新增地区时，不能只换配色或贴图。每个地区必须定义四件事：

1. **连接方式**
   - 这个地区如何停靠、通行、传递信息。
   - 例：绳索悬挂、木梁斜撑、环形码头、灯塔网、帆布廊道。

2. **生活方式**
   - 居民如何工作、储物、交易、修补和等待航线。
   - 生活痕迹必须能在建筑、道具、NPC 和路径里看见。

3. **修复问题**
   - 这个地区主要坏在哪里。
   - 例：断缆、信标失准、平台失衡、云雾堵塞、旧航线失联。

4. **修复回应**
   - 玩家反哺后，这个地区具体如何改变。
   - 例：灯塔复亮、集市重开、航线回流、居民动线恢复、新补给开放。

地区扩展必须先完成这四项，再进入视觉草案。

### 9.5 扩展角色规则

后续新增角色必须先回答：

- 他/她是谁。
- 和飞艇、航路、村镇或修复有什么关系。
- 玩家在 3 秒内靠什么读出身份。
- 远距、中距、近距分别读什么。
- 是否有一个清晰功能动词。
- 是否保留生活痕迹或修补痕迹。

角色优先按功能和关系扩展，不按稀有度、职业模板或视觉噱头扩展。

#### 9.5.1 新伙伴

新增伙伴只能有一个主功能动词。例：

- 侦察。
- 整备。
- 交易。
- 修缮。
- 记录。
- 引航。

伙伴之间不能互相抢功能。每个伙伴的视觉记忆点必须服务自己的功能动词。

#### 9.5.2 新 NPC

新增 NPC 必须先读职业，再读地方，再读情绪。

普通 NPC 不允许拥有比核心伙伴更强的信号色、夸张轮廓或主视觉装置。NPC 的价值来自让世界可信，而不是成为孤立展示角色。

#### 9.5.3 新危险单位

新增危险单位必须表达一种连接破坏：

- 断裂。
- 错接。
- 漏风。
- 失衡。
- 逆流。
- 堵塞。
- 失准。
- 失联。

如果危险单位只是在“攻击玩家”，但无法说明它破坏了什么连接，则方向不通过。

### 9.6 扩展 UI 规则

新增 UI 必须从以下语义里选择来源：

- 航图。
- 挂签。
- 修补记录。
- 船员牌。
- 仪表。
- 航标。
- 封条。
- 货架。
- 收纳网。

新增 UI 不应引入与世界无关的视觉系统。新增面板必须继承第 7 章的 HUD、航图、整备、搜撤和修复反馈规则。

#### 9.6.1 新图标

新增图标必须先定义大类：

- 路线。
- 修复。
- 风险。
- 资源。
- 伙伴。
- 地点。
- 状态。

图标要通过 24px、32px、48px 三档检查。不能通过小尺寸检查的图标不得作为核心状态图标。

#### 9.6.2 新界面

新增界面必须说明：

- 它服务哪个决策。
- 它是否支持键鼠。
- 它的常驻信息和临时信息分别是什么。
- 它如何避免遮挡世界。
- 它如何把结果接回世界反哺。

不能说明这些内容的界面不应进入实现。

### 9.7 扩展资产规则

新增资产必须进入资产清单，并标注：

- 所属系统。
- 使用场景。
- 状态变体。
- 是否交互。
- 是否动画。
- 是否影响性能。
- 对应 Art Bible 章节。

任何关键玩法资产都不能只有单一静态态。至少要明确是否需要受损、临修、复通、禁用、激活或选中状态。

### 9.8 美术与设计的交叉检查

美术不能独立于设计推进。以下设计变化必须触发 Art Bible 检查：

- 新增核心玩法循环。
- 新增飞艇模块类型。
- 新增资源类别。
- 新增村镇或地区。
- 新增伙伴系统。
- 新增危险类型。
- 新增搜撤规则。
- 新增 UI 主界面。

检查重点：

- 是否需要新颜色语义。
- 是否需要新形状语法。
- 是否会破坏现有 UI 层级。
- 是否会引入与航路修复主义冲突的视觉方向。
- 是否会超出 Web-first 2D 的制作与性能边界。

若设计变更无法被现有 Art Bible 支持，应先更新 Art Bible，再进入资产制作。

### 9.9 风格偏离诊断

当画面感觉“不像《云海织航》”时，按以下顺序诊断：

1. **是否太战斗化**
   - 是否武器、尖刺、护甲、红黑冲突过多。
   - 是否把危险表现成敌人炫技，而不是连接破坏。

2. **是否太科技化**
   - 是否出现大量蓝紫玻璃、霓虹线框、纯现代 HUD。
   - 是否失去手工、补痕、旧材料和生活痕迹。

3. **是否太童话化**
   - 是否过度柔软、可爱、低风险。
   - 是否削弱了未知航线和搜撤取舍的判断压力。

4. **是否太脏乱**
   - 是否所有东西都破损，导致修复结果不明显。
   - 是否看不出路径、功能、状态。

5. **是否太装饰化**
   - 是否大量花纹、挂件、纹样没有功能来源。
   - 是否抢过路径、交互和状态信息。

6. **是否太抽象**
   - 是否看不出谁住在这里、如何停靠、如何修复。
   - 是否只有概念感，没有生产和生活逻辑。

诊断后应回到对应章节返工，而不是新增临时风格规则。

### 9.10 硬红线

以下规则不可被单个资产、单个角色或单个地区突破：

- 不能牺牲可读性换取画面复杂度。
- 不能把飞艇表现成纯战斗载具。
- 不能把世界成长表现成奢华替换。
- 不能把危险常态化为大面积红黑压迫。
- 不能让 UI 脱离航图、修补记录和航标系统。
- 不能只靠颜色表达关键状态。
- 不能让搜撤场景变成纯清怪地牢。
- 不能让村镇成为静态布景，必须体现生活与航路关系。
- 不能制作没有状态计划的关键修复资产。
- 不能把 Web 性能问题推迟到最终阶段。

### 9.11 最终美术签核清单

每个重要美术方向在进入正式制作前，必须完成以下签核：

- **视觉身份**：是否仍然是航路修复主义。
- **情绪基调**：是否保持可回家、可规划、可照料。
- **形状语言**：是否体现连接、修补、节点、断裂或复通。
- **颜色系统**：是否正确使用生活色、功能色和危险色。
- **角色规则**：是否先读身份，再读关系，最后读情绪。
- **环境规则**：是否说明停靠、生活、损坏和修复。
- **UI 规则**：是否像航行工作台，而不是外部皮肤。
- **资产规则**：是否命名、分层、状态、导出都可执行。
- **性能规则**：是否适合 Web-first 2D。
- **扩展规则**：是否能支持后续地区、角色和系统继续发展。

### 9.12 本章结论

《云海织航》的美术方向不追求“最壮观的天空”，而追求一个玩家愿意反复回到其中、逐步修好它的世界。

所有美术资产最终都要回答同一个问题：

**它是否让玩家更相信，这片云海中的人、船、路和村镇值得被重新连接？**

如果答案是肯定的，它就在服务本项目的核心视觉身份。  
如果答案不清楚，就必须回到前面的章节重新校准。
