# 场景 / UI / 单位创建适合性人工审查门禁

> **最后更新**: 2026-05-24
> **适用范围**: 任何新建可进入场景、运行时 UI 表面、可复用场景单位、`scene_unit.prototype.*`，或等价的世界对象 / 面板 / 覆盖层。
> **目的**: 在写实现或把规格标为 `implementation_ready` 前，先由人判断“这个东西是否适合进入项目”。
> **边界**: Codex 可以起草、整理证据和提出建议；不能替代人工适合性批准。

## 硬规则

任何想要创建以下内容的 story、规格或运行时改动，都必须先有人工适合性审查记录：

- 新的可进入场景、路线目的地、市场 / 修复 / 探索区域、场景转场或世界可玩空间。
- 新的持久 HUD、锚定面板、模态 / 半模态覆盖层、全屏 UI、toast / hint、debug overlay、输入 / 焦点规则或显示优先级。
- 新的固定单位、动态实体、NPC、障碍物、门、资源点、可推动 / 移动物、带碰撞 / 遮挡 / 状态的 prop，或 `scene_unit.prototype.*`。

流程固定为：

1. Codex 发现需要新建或替换 `scene` / `ui` / `unit` 时，先提出创建申请。
2. 人工只审核“是否适合创建”；结论为 `APPROVED` 或 `APPROVED_WITH_NOTES` 才能继续。
3. Codex 起草对应规格，并把人工备注写回规格。
4. 不再设置规格二次人工审核硬门；规格满足模板、备注已写回、独立实现 / 资产边界明确后，可进入实现。
5. 实现后用自动证据、截图 / 视觉证据和用户体验验收关闭当前轮次。
6. 已验收内容仍保持可修改；后续按 `directed-content-modification` 对指定场景 / UI / 单位定向修改规格和实现。

没有人工适合性审查时：

- story-readiness 必须给 `BLOCKED`，除非该 story 的唯一目标是起草审查包或规格草案。
- `/dev-story` 必须在编码前停止，不能把“正在问用户”当作已经批准。
- 规格生命周期不能进入 `implementation_ready`。
- 运行时数据、C# 代码、Godot 场景或测试夹具不能新增对应实体，除非只是为了生成审查材料且明确标为非生产实现。

## 旧 Godot 节点处理

门禁出现前的不合规旧 Godot 节点不能因为“已经存在”而保留、转正或补写 legacy 规格。触碰旧节点时，Codex 必须先识别它是否已有合规的 scene / ui / unit 规格和人工适合性审查。

若旧节点不合规：

- 默认处理方向是删除或替换，而不是保留。
- 删除前必须向用户确认，说明要删除的节点、所在文件、删除原因和可选替代路径。
- 如果用户希望保留旧概念，必须把它当作全新内容重新走创建申请、规格和独立实现 / 资产边界确认。
- 旧节点存在本身不能作为创建适合性、场景完整性、单位规格或 UI 规格证据。

## 独立实现 / 独立资产边界

每一个通过本门禁创建的场景、UI 或单位都必须有可追踪的独立边界。它可以是一个独立实现、一个独立资产，或一组命名清楚、能整体引用的资产 / 数据 / 场景文件。

| 类型 | 独立边界要求 |
| --- | --- |
| 场景 | 独立可进入场景通常应有独立 `.tscn`，并可配套独立 C# runtime、作者化数据、资产目录或证据文件。 |
| UI | 独立 UI 表面应有独立 `.tscn`、独立组件或明确注册表条目；不能隐式混入无关 UI 容器。 |
| 单位 | 可复用单位原型应有独立 Godot 场景、资源、数据原型或一组可整体追踪的资产；摆放实例只引用原型，不等同于新单位。 |

禁止把新场景、UI 或单位只散落写进大型运行时脚本、旧灰盒场景或临时节点树中。大型脚本 / 场景可以装配和引用已经独立存在的对象，但不能成为对象本体。

## 审查结论

| 结论 | 含义 | 是否允许开工 |
| --- | --- | --- |
| `PENDING` | 尚未审查或证据不足。 | 否 |
| `APPROVED` | 适合进入项目，可继续补规格和实现。 | 是 |
| `APPROVED_WITH_NOTES` | 适合进入项目，但必须把备注写回规格 / story。 | 是，备注是必做项 |
| `REVISE` | 方向可能可行，但需要改概念、边界、命名、交互或摆放。 | 否 |
| `REJECTED` | 不适合当前项目、阶段、幻想、范围或质量目标。 | 否 |

只有 `APPROVED` 和 `APPROVED_WITH_NOTES` 解除创建门禁。

## 最低审查记录

人工审查记录可以写在对应规格文件、story、playtest 记录或独立 evidence 中，但必须包含：

| 字段 | 要求 |
| --- | --- |
| 创建对象类型 | `scene` / `ui` / `unit` |
| 稳定 ID 或拟定 ID | 如 `scene.old_market_edge`、`S13_example`、`scene_unit.prototype.example` |
| 人工审查人 | 用户、制作人、设计负责人或明确的人类 reviewer |
| 审查日期 | 使用具体日期 |
| 审查问题 | 至少回答本文件对应类型的问题 |
| 结论 | `PENDING` / `APPROVED` / `APPROVED_WITH_NOTES` / `REVISE` / `REJECTED` |
| 必须回写的备注 | 没有则写 `None` |

## 审查问题

### 场景

- 这个场景是否服务当前核心幻想、循环节点和项目阶段？
- 玩家为什么需要进入这里，而不是用现有场景或 UI 解决？
- 它是否引入新的世界对象、物理规则、状态或资产负担？
- 它与已有场景是否重复、冲突或造成范围膨胀？
- 这个场景的 3 秒识别目标是否清楚？

### UI

- 这个 UI 是否真的需要新表面，而不是复用现有 HUD / 面板 / 模态？
- 它是否只承担解释、选择、确认、反馈或无障碍补充，而不是替代世界对象？
- 它的显示优先级和输入 / 焦点影响是否适合当前流程？
- 它会不会让玩家只是在点 UI，而不是理解场景和世界动作？
- 它绑定的系统状态或世界锚点是否明确存在？

### 单位

- 这个单位是否是玩家能理解的真实世界对象或实体？
- 它是否需要独立原型，而不是已有单位的状态、皮肤或摆放实例？
- 它的碰撞、遮挡、比例、交互和生命周期是否符合当前场景需要？
- 它是否带来新的领域状态、持久化、AI、物理或资产复杂度？
- 它能否被现有固定单位 / 动态实体分类清楚表达？

## 与规格目录的关系

- 通过本门禁只表示“适合创建”，不表示规格完整。
- 通过后仍必须补对应规格：
  - 场景: `production/scene-specs/`
  - UI: `production/ui-specs/`
  - 单位: `production/unit-specs/fixed-scene-objects/` 或 `production/unit-specs/dynamic-entities/`
- 如果人工备注要求修改方向，规格必须先吸收备注，再进入 `implementation_ready`。
- 规格二次人工审核不是硬门；用户可随时提出修改，但不阻塞已通过适合性审查且规格完整的下一步实现。
- 体验验收通过不表示内容冻结。后续对已存在对象的修改走定向修改流程；只有新增对象才重新触发本门禁。
